# Phase 3 — the Docker cap did not hold, and the cap was on the wrong directory

`bunne-test`, 2026-08-21. `~/t-docker-quota.sh` was run as root by the author at
**16:01:51** (`sudo` log, boot `-1`). Its stdout went to his terminal and was not
captured, so **everything below is reconstructed from the journal and from the
state left on disk** — which turns out to be the more useful record anyway.

**Headline: `cap_enforced=0`. The 2 GiB qgroup limit never refused a write.**
That is a null result, not a verdict on qgroups — the harness had two flaws that
made the cap untestable, and it also capped a directory that Docker 29 no longer
stores images in.

## What the script actually did

| step | evidence | outcome |
|---|---|---|
| `btrfs quota enable /` + `rescan -w` | `BTRFS info (device dm-0): qgroup scan completed (inconsistency flag cleared)` @ 16:01:57 | worked |

| fill loop, 40 × 256 MiB | 39 `task-delete` events, 16:04:01 → 16:04:50 (49 s) | **ran to the end — zero refusals** |
| snapshot probe | — | ran; result not captured |

Host free space today: **117 G free of 129 G, 9% used.** Nothing accumulated.

## Why the cap could not bite — two flaws in the harness

1. **`--rm` frees each blob before the next one is written.** Every iteration is
   a fresh `docker run --rm alpine`, so the 256 MiB lands in that container's
   writable layer and the layer is destroyed the instant the container exits.
   Peak usage is 256 MiB, not 10 GiB. A 2 GiB cap can never be reached by a
   workload that never holds more than 256 MiB at once.
2. **The `-v /tmp:/out` bind mount is unused.** The `dd` writes to
   `/var/tmp/blob` *inside* the container, not to `/out`. Harmless here, but it
   means the mount states an intent the script does not carry out.

Neither flaw is subtle in hindsight; both are invisible from the script's own
output, which is exactly why the run produced a confident-looking `cap_enforced=0`.

## The finding that outranks both — `/var/lib/docker` is the wrong target

Docker on Arch is now **29.7.2**, and it started with:

```
msg="Starting daemon with containerd snapshotter integration enabled"
msg="Docker daemon" containerd-snapshotter=true storage-driver=overlayfs version=29.7.2
```

There is **no `/etc/docker/daemon.json`** on this machine, so that is the stock
default, not a local choice. `containerd` runs as its own systemd unit
(v2.3.4, started 16:01:57), and it logged its own root directory:

```
"containerdRootDir":"/var/lib/containerd"
"rootDir":"/var/lib/containerd/io.containerd.grpc.v1.cri"
```

Under the containerd snapshotter, image layers and container snapshots are
containerd's objects, kept beneath `/var/lib/containerd/`. What appears under
`/var/lib/docker` is the *merged* overlay mount per running container —
the systemd units are named `var-lib-docker-rootfs-overlayfs-<id>.mount` — while
the `upper`/`lower` directories those mounts are assembled from live in
containerd's snapshotter directory.

**So a qgroup on a subvolume mounted at `/var/lib/docker` caps a view, not the
bytes.** `/var/lib/containerd` sits on `@`, uncapped, alongside the root
filesystem — which is precisely the failure mode `docker-storage-quota` exists to
prevent. This also means the `snapshot-bloat` half is *worse* than assumed: the
image bytes are on `@`, so they land in every snapshot of `@`.

**Confirmed:** the daemon's configuration and containerd's root path, from their
own logs. **Not yet confirmed:** that the bytes follow the configuration. That
needs one `du -sh /var/lib/docker /var/lib/containerd` either side of pulling a
large image, and it needs root. Do not write this into `CHOICES.md` as settled
until the `du` exists — the whole point of this file is that a plausible
mechanism is not a measured one.

## What v2 has to do differently

`~/t-docker-quota2.sh` (written, not yet run — needs root):

- **Hold the data.** Pull real multi-GB images and keep them, or use one
  long-lived container, instead of 40 disposable ones. Images are what filled the
  author's disk; images are what the test must grow.
- **Locate the bytes first, cap second.** `du` both directories before deciding
  what the subvolume should be mounted at. If the bytes are in
  `/var/lib/containerd`, the subvolume belongs there — or `data-root` and
  containerd's root both need pointing into one capped subvolume.
- **Capture stdout.** `| tee ~/log-t-docker-quota.log`. This run's numbers were
  recoverable only because systemd happened to log the container churn.
- **Report the qgroup number even on success**, so a run that fills nothing is
  visibly distinguishable from a run that filled a lot and was allowed to.

## Bearing on the decisions

- `docker-storage-quota` stays **deferred**. Candidate (2), the qgroup subvolume,
  is neither confirmed nor refuted — it was aimed at a path that no longer holds
  the data. Candidate (1), `overlay2.size=`, is now *also* in question: with
  `containerd-snapshotter=true` the `overlay2` driver is not in use at all.
- `snapshot-bloat` part (1) — "Docker must never land in a snapshot" — cannot be
  closed by the nested-subvolume trick alone until the byte location is settled.
