Gripe #3's home. Candidates: **LazyVim** (author's current daily),

## Pre-registered, phase 1 (committed before any install)

- Target: `nvim <file>` to editor-usable on a **real 1500-line Python
  file** (generated, committed as `benchmarks/instruments/gen-testpy.sh`
  output — same shape as the 3.9 method).
- Instrument: `nvim --startuptime` (its own final line), n=10 per
  candidate per boot, first run of each labeled cold, load recorded; bare
  `nvim` (no config) measured as the floor each session.
- Preconditions, per candidate: plugins fully synced headlessly BEFORE
  measuring (no first-run installs in the timing); `python-pynvim`
  installed and `g:python3_host_prog` pinned in all three (the 3.9 fix —
  otherwise every candidate pays a ~34 ms failing-probe tax that measures
  nothing about the candidate).
- Decision rule (phase 1 only ranks; nothing closes on startup alone):
  candidates within 25 ms of each other at median are a startup tie —
  phases 2 (gr correctness+latency) and 3 (molten render, the actual
  gripe) decide. A candidate >150 ms median is flagged against 2a but
  still runs phases 2-3 (features may justify it; the author decides).
- NVChad-specific check: its `loaded_python3_provider = 0` default must be
  detected and reverted in the throwaway config, and that fact recorded —
  it would silently break molten (the `jupyter-in-neovim` cautionary tale).

## Phase 3 result (NVChad candidate) — one render, provisional, mirrors the nix side's rounds-6-7 caveats

**The gripe rendered**: molten + image.nvim (`magick_cli` backend) inside
NVChad inside kitty on the fresh Arch install produced a real inline
matplotlib chart (`Out[2]: ✓ Done 0.0s`, the [1,2,3]/[4,1,9] plot,
visually verified against the plotted data from the screenshot —
`scratchpad` screenshots archived in the session). ONE warm-session
render after several driven attempts — explicitly NOT "gripe 3 solved on
Arch"; fresh-boot first-try repeatability untested, same labeling
discipline as nix-bunne's ledger row for its render.

**The four findings that matter more than the render:**

1. **NVChad ships a SECOND silent molten-killer**: `"rplugin"` sits in its
   lazy.nvim `performance.rtp.disabled_plugins` list, so
   `:UpdateRemotePlugins` does not even exist and no remote plugin can
   ever register — on top of the known `loaded_python3_provider = 0`.
   Both are one-line reverts; both fail with zero announcement. If NVChad
   wins this bake-off, these two reverts are mandatory config, called out
   loudly.
2. **The missing Jupyter runtime dir reproduced on the fresh install** —
   the exact session-4 bug (`~/.local/share/jupyter/runtime` absent;
   molten's kernel init dies on Errno 2). Whatever ships must create it
   (or the venv bootstrap must). "What do our configs invoke that we
   never install/create" strikes again, on schedule.
3. **lazy-by-default eats remote plugins quietly**: molten needs
   `lazy = false` (or explicit triggers) under NVChad's lazy.nvim
   defaults, and the rplugin manifest must be regenerated AFTER the
   plugin actually loads — a manifest generated while the plugin was
   lazy-unloaded is silently empty.
4. **The fail-loudly image gate works**: the throwaway config's
   not-inside-kitty warning fired on every headless invocation —
   the predecessor's silent-gate lesson, honored and exercised.

## Correction 2026-08-25 (overnight): the lock mechanism, refined at the source

The phase-2 side finding's mechanism guess ("a locked niri session doesn't
map new windows") is **wrong in a way that matters**: the spawn is dropped
**before any fork happens**, not spawned-and-hidden. Established on the
NixOS half of the same laptop, same niri 26.04 (nix-bunne DA round 15,
`da-logs/niri-locked-spawn-2026-08-25.md`): with the session locked, every
IPC `spawn`/`spawn-sh` returns rc=0 while `strace -f` across all 22 niri
threads records **zero clone/execve**, no systemd scope is created, and
nothing is logged. Source (niri v26.04 tag): `do_action` early-returns when
`is_locked()` unless the action is whitelisted (`allow-when-locked=true` is
the config-side face of the same gate); the IPC server passes
`allow_when_locked: false` and replies `Handled` unconditionally.
Consequences: (a) no process ever starts, so nothing leaks or queues — the
locked box is exactly as clean as before the attempt; (b) `niri msg`'s
exit code cannot distinguish done-from-dropped while locked (upstream UX
paper cut; report candidate, author's call); (c) the one-line diagnostic
whenever spawns "mysteriously" do nothing: **`pgrep -x swaylock`**.

**Correction, 2026-08-25 (session 4.24): the one-liner as first written was
`pgrep -f swaylock`, and it always answers "locked".** `-f` matches the whole
command line, and the shipped config's own idle watcher is
`swayidle -w timeout 900 "swaylock -f -c 0f0f0f" ...` — the string `swaylock`
sits in swayidle's arguments, so `pgrep -f swaylock` matches the *watcher* on
every running session, locked or not (it also matches the shell asking the
question). Caught by using it: it reported LOCKED on a fresh unlocked boot, on
which an IPC spawn then worked. `pgrep -x swaylock` matches the process *name*
exactly and is right in both directions — verified live, `no swaylock process`
on an unlocked session whose spawn canary succeeded. A diagnostic that is
wrong in the direction of the bug it diagnoses is worse than none: it would
have sent the next reader looking for a lock that was not there.

Two caveats the replacement carries, so the fix does not become the same
failure one layer down (both raised in DA round 18): **`pgrep -x` matches the
process *name* exactly**, so it answers "unlocked" for `hyprlock`, `gtklock`,
or any wrapper not literally called `swaylock` — correct for BunnE, which ships
swaylock (`CHOICES.md` `lock-idle`), and wrong the moment the locker changes.
And **the box this was demonstrated on runs a 28800 s idle timeout** instead of
the shipped 900 s (a documented test-rig deviation), which is why a
one-minute-old session had no locker at all; the finding is about argv matching
rather than timing, but "verified in both directions" was verified on a session
that could not have locked.

(unlocked IPC spawn canary created, niri 26.04/8ed0da4); deliberate
lock → drop → reboot-recover control scheduled with the next planned
reboot.
