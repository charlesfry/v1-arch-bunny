## Phase A — where the bytes actually go (3.11's hypothesis, now measured)

Three retained 256 MiB incompressible images (`docker import`, no
containers, nothing `--rm`):

| | /var/lib/docker | /var/lib/containerd |
|---|---|---|
| baseline | 213 KB | 66 KB |
| after 3 imports | **213 KB (unchanged)** | **1.61 GB** |

Each image costs ~537 MB there — the 256 MiB blob twice (content store +
unpacked overlayfs snapshot). **This is the zero-sharing worst case** (every
test layer unique urandom); real stacks share layers, so it is a cap-sizing
upper bound, not a typical growth rate. **`/var/lib/containerd` is the directory that
matters; `/var/lib/docker` holds metadata.** (Caveat for the real design:
docker *volumes* live under `/var/lib/docker/volumes` and were not
exercised — user data through volumes would grow the other directory.)

## Phase B — the cap, and TRAP #1: the naive setup silently doesn't enforce

`/var/lib/containerd` moved onto its own btrfs subvolume (0/271), qgroup
limit 2 GiB, docker restarted, filled with 256 MiB imports:
**12/12 imports succeeded — 8 GB written against a 2 GiB limit.
`cap_enforced=0`.** The qgroup showed `0.00B` accounted throughout, with
"qgroup data inconsistent, rescan recommended" at limit-set time, and dmesg
saying it plainly: `qgroup marked inconsistent, qgroup inherit needs a
rescan`. **While qgroups are inconsistent, limits do not enforce.** The
row's candidate (2) as written — "size-capped btrfs subvolume + qgroup" —
ships a silent no-op unless a rescan follows subvolume creation. This is
the same silent-null-cap failure shape as 3.11, now with its mechanism.

After `btrfs quota rescan -w /`: accounting went live and the **4th import
was refused** *(evidence label: this paragraph's session was reconstructed,
not tee'd — `raw/4.5.followup.log`; the independently tee'd refusal is
4.5b's trap-7 import 3, which supersedes this as evidence)*:

```
failed to extract layer ...: write .../blob.bin: disk quota exceeded
```

**`cap_enforced=1`** — refused at the arithmetic point (3 × 537 MB ≈
1.61 GiB; a 4th would exceed 2 GiB), loudly, through Docker's own error
output, while the filesystem had 237 GiB free. Fail-loudly satisfied by the
mechanism itself.

## Phase C — TRAP #2: at the cap, containerd wedges (can't add OR delete)

With the qgroup pinned at 2.00/2.00 GiB, `docker image rm` **also failed**:
`write .../io.containerd.metadata.v1.bolt/meta.db: disk quota exceeded` —
deletion requires writing the metadata DB, which the full quota refuses.
The classic disk-full trap in miniature: a hard cap with zero headroom is a
one-way door.

*(Evidence note, DA r1 #6: the scripted log's earlier `recovery_ok=1` was
recorded BEFORE any rescan — the quota was not enforcing at that moment, so
it proves nothing about recovery from a real wedge; the recovery that
counts is 4.5b's tee'd sequence below/above.)*

**Recovery procedure, proven (tee'd in 4.5b):** `btrfs qgroup limit 4G 0/271 <path>` →
deletes succeed → re-limit to 2 GiB → normal import AND delete both work
again. One command, no data loss, no docker restart needed. The real
design should either keep headroom between "alert" and "wall," or document
this bump-clean-relimit procedure next to the cap.

Residual: after the wedge episode and full image cleanup, ~505 MiB of
content remained in the subvolume (containerd's own GC semantics — not
chased tonight; understand before sizing the production cap).

## Also proven — the snapshot-bloat mechanism (gripe #2's docker half)

`snapper create` while the subvolume held gigabytes: the snapshot's
`/var/lib/containerd` is an **empty directory — 0 entries**. Nested
subvolumes are genuinely excluded from root snapshots on this exact layout.
Docker bytes can never bloat `@` snapshots again once this design lands.
