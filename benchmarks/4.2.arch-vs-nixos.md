**Revision 3** — rounds 1 and 2 both DA-rejected (r1: mislabeled Ns, missing

**What this file is:** the first cross-OS dataset in either repo collected
with ONE instrument set on both sides — `spawnbench.py` (raw niri IPC socket
poller, no CLI exec in the measured path), `pss-sum.sh` (root smaps_rollup
PSS sums), `systemd-analyze` — same hardware, same hour, same niri session
composition (both configs derive from the same config.kdl; identical
spawn-at-startup list). Every measurement line carries its own load1 in
`raw/`; see the load note below for the honest envelope per dataset.

**What this file is NOT:** it does not close `CHOICES.md` `os-base`. That
row demands a measured verdict with author-set thresholds; none were
pre-registered before tonight's collection, so everything below is
characterization, not verdict. Proposed thresholds for the closing round are
at the bottom, written BEFORE any future data collection.

> **Annotation 2026-08-24 (post-4.8): the kitty rows below carry a
> driver-stack confound.** All Arch numbers in this file were taken with
> firmware-less nouveau (no nvidia userspace installed); NixOS ran
> nvidia-open. `4.8.kitty-post-nvidia.md` shows the nvidia EGL ICD costs
> kitty **~7–10 ms** warm per launch via glvnd enumeration
> (block-interleaved within-boot A/B, DA-gated in 4.8b rounds 1–2).
> **Resolved by 4.9 (DA-gated, survives with caveats):** NixOS kitty
> pays the same tax — roughly 10-12 ms on its driver 595 — so the
> ~23 ms gap in this table was ≈ NixOS's ICD tax stacked on a **roughly
> 10-12 ms as-shipped OS gap** (pinned-vs-pinned: Arch ~132-134 vs
> NixOS ~144; coarse quoting per DA — 2-vs-5 boot asymmetry, mixed
> median estimators, kernel-generation confound named in 4.9). Arch
> remains faster; the OS-attributable margin is about half what this
> table suggested. The
> fuzzel control is unaffected in-process (zero EGL maps) but shifted
> ~+1 ms post-nvidia, unattributed. The niri idle-PSS oddity (Arch 82.7
> vs NixOS ~94 MB) was also taken pre-nvidia on Arch and niri now maps
> the nvidia stack — that open question needs re-measuring before anyone
> reasons from it.

## Warts and limitations (all of round 1's, kept on the record)

1. NixOS warm spawn = 2 boots (instrument teardown didn't know NixOS names
   processes `.kitty-wrapped`; fixed, disclosed; colds from all 5 boots
   kept — the "3 colds" in revision 1 was a mid-collection snapshot, not
   selection, and all 5 are now shown).
2. fuzzel is a thin control: it clears the compositor/IPC/spawn path of
   blame for the kitty delta, but cannot distinguish *which part* of
   kitty's bring-up (wrapper exec, store-path linking, build flags,
   runtime) differs — the attribution is "kitty's own startup path on each
   OS," nothing more specific.
3. Post-hoc decomposition instead of pre-matched configs (see RAM section
   for why); interaction effects between components are not captured.
4. Kernel versions differ (above). Session composition beyond the spawn
   list differs where noted.
5. No significance testing; per-boot min/med/max is the honesty offered.
   Boot-count asymmetries are labeled per table.

## Proposed thresholds for an os-base closing round (pre-registered now)

Written before any future collection; the author owns the final numbers:
- 2a: a ≥15% median difference, reproduced across ≥3 boots per side with
  matched loader timeouts and same-version kernels where feasible, on
  keystroke-path metrics (spawn, desktop-ready).
- 2b: a ≥50 MB difference in like-for-like session PSS with matched
  service composition (or fully-itemized deltas).
- Anything smaller: declare parity and decide `os-base` on priority-1
  grounds (maintenance model, breakage behavior), not performance.
