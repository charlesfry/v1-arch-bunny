# Phase 3 — the first measured graphical session

`bunne-test`, 2026-08-21, **idle (load 0.25)**, niri + the five slots installed
that day. First time a *running desktop* has been measured with everything
started; `3.2` measured an empty compositor.

## Terminal spawn — the number that was missing

Metric: **spawn → a shell is actually running inside the new window.** Chosen
because `kitty --single-instance` returns as soon as it has handed off to the
running process, so naive timing reports 1.7 ms for a window that does not exist
yet. Both modes are measured the same way.

| Mode | Spawn → shell in window |
|---|---|
| cold — new kitty process each time | **178.9 ms** |
| warm — `--single-instance` reuses the process | **15.6 ms** |

**11.5x, and it crosses the perception threshold**: ~180 ms is visibly slow for
the machine's most-used application; ~16 ms is not.

**The cost is kitty itself, not our config.** Measured `kitty sh -c exit`
end-to-end three ways:

| Variant | Time |
|---|---|
| default (our 3-line config) | 215.4 ms |
| `--config NONE` | 213.5 ms |
| `-o shell_integration=disabled` | 216.5 ms |

Identical within noise. There is nothing to tune in the config — the only lever
is not starting a new process. For reference on the same machine: bare process
spawn 1.3 ms, `fuzzel --version` 5.0 ms.

**Open**: `--single-instance` means one process serves every window, so a crash
takes all terminals at once, and the *first* window still costs 178.9 ms. Needs
adding to niri's `Mod+T` binding to take effect. **Also unresolved: this is the
kitty-vs-ghostty tiebreak** (`CHOICES.md` `terminal`, still `trying`) — ghostty
must now beat 178.9 ms cold, or match kitty's single-instance behaviour.

## Three ledger claims that did not survive contact

**1. The portal is 96 MB resident, not "0 MB at idle".** `CHOICES.md` `portal`
says *"the portal processes themselves are 0 MB at idle"* — measured in a live
session they are **19.2 + 45.9 + 31.0 = 96.1 MB across three processes**. The
row's `+46.8 MB` session delta was measured before anything had *used* a portal;
once activated they stay. This is the single largest correctable item on the
machine.

**2. `xdg-desktop-portal-gtk` is running and nobody chose it.** 31.0 MB. Our
`portals.conf` says `default=gnome;gtk;` — the `gtk` fallback got started too.
**Untested and worth testing: drop `;gtk` and see whether anything breaks.** If
screen sharing still reports `AvailableSourceTypes = 7`, that is 31 MB for free.

**3. `mako` at 9.1 MB confirms the row, with a caveat worth stating.** The unit
is `disabled` by preset and mako was nevertheless running, i.e. **D-Bus
activated exactly as the row predicts** — but it started at 13:00:31 and stays
resident. So "0 MB until the first notification" is true and misleading: on a
desktop that shows notifications, the steady state is 9.1 MB, not 0.

**Unaccounted residents**: `gvfsd` (14.5 MB) and `upowerd` (13.9 MB), both
started by systemd, neither traceable to a ledger row. `gvfsd` is predicted by
the `portal` row's dependency chain (portal → nautilus → gvfs). `upowerd` is
power/battery status — note `03-alternatives.md` dropped
`power-profiles-daemon`, which is a different package; this one arrived
unasked. **28.4 MB between them, and Phase 4's "done" criterion says every
package traces to a ledger row.**

## Follow-up 1: dropping `;gtk` — tested, 30 MB, not free

`portals.conf` changed from `default=gnome;gtk;` to `default=gnome`, portal
restarted, screen sharing re-probed:

| | before | after |
|---|---|---|
| `AvailableSourceTypes` | 7 | **7** |
| `AvailableCursorModes` | 7 | **7** |
| `xdg-desktop-portal-gtk` | 30.1 MB | **gone** |

**Screen sharing is provably unaffected**, but one probe is not the whole story.
Comparing the two backends' `.portal` files, GTK uniquely provided **two**
interfaces GNOME does not:

- **`Email`** — apps requesting a mail composer. Nothing here uses it.
- **`Inhibit`** — prevents idle/sleep. Native Wayland apps use
  `zwp_idle_inhibit_manager_v1` directly, but sandboxed ones go through the
  portal. **Untestable right now** because the lock/idle slot is undecided —
  **re-test when it lands**: play a video and confirm the screen does not blank.

## Follow-up 2: why kitty is slow, and it is not this machine

The 178.9 ms looked implausible, so it was checked rather than accepted.

**Hypothesis tested and mostly rejected — NVIDIA EGL init.** The `browser` row
found glvnd dlopening 32.9 MB of NVIDIA libraries on this hybrid laptop for a GPU
Brave never touches, so kitty seemed likely to pay the same. Restricting EGL to
Intel with `__EGL_VENDOR_LIBRARY_FILENAMES=.../50_mesa.json` moved it from
**216.1 ms to 205.5 ms** — real, but 10 ms of 216. Not the answer.
(`LIBGL_ALWAYS_SOFTWARE=1` made it worse at 291.7 ms, as expected.)

**The actual cause is architectural.** kitty's memory maps show a full **CPython
3.14 interpreter** — `_bisect`, `_bz2`, `_ctypes`, `_json`, `_lzma`, `_socket`,
`_struct`, `binascii`, `fcntl` and more, all `.cpython-314-x86_64-linux-gnu.so` —
across **100 distinct shared objects**, with 304 MB RSS. kitty is a Python
application with a C core, and it pays interpreter startup on every window.

**Cross-checked against published figures**, since one machine proves nothing.
Upstream issue [kovidgoyal/kitty#4292](https://github.com/kovidgoyal/kitty/issues/4292),
"Slow start up time as compared to alacritty", reports **kitty 0.251 s vs
alacritty 0.165 s**. Our 0.215 s end-to-end sits inside that range, so **this is
kitty's normal behaviour, not a fault of this laptop**. The reporter attributes
it to `load_all_shaders` — GPU shader compilation at every startup — on top of
the interpreter, and proposes shader caching, sprite-map caching, and compiling
the Python with Nuitka or Cython. None of that is in a release.

**Consequence: the terminal slot should not close on kitty by default.**
`ghostty` is `extra/ghostty 1.3.1-2`, written in Zig, **no Python in its
dependency list**, and it implements the kitty graphics protocol — which is the
only reason kitty won C5 in the first place. It was ranked candidate 2 explicitly
to "win on latency, and only then on weight". This is that test.

# Addendum — niri's 305 MB is not a leak (2026-08-21)

`BUDGET.md` flagged niri's apparent growth — **115 MB early in a session, 172 MB
later, 305 MB in a fresh 20-minute session** — as the largest open question in
the RAM bucket. Chased to a conclusion rather than sampled indefinitely.

## Its own memory is 30 MB

Largest mappings, measured with **zero windows open**:

| Mapping | RSS | What it is |
|---|---|---|
| `libLLVM.so.22.1` | **85 MB** | Mesa's shader compiler |
| `libnvidia-gpucomp.so` | **69 MB** | NVIDIA driver |
| `libgallium.so` | 42 MB | Mesa |
| `libnvidia-eglcore.so` | 21 MB | NVIDIA driver |
| `/usr/bin/niri` | 20 MB | the compositor itself |
| `[heap]` | **30 MB** | niri's actual data |

**241 MB of the 305 is shared libraries.** By category: 241 MB `.so`, 12 MB
DRM/device nodes, 7.5 MB anonymous. The growth is those libraries **paging in
lazily** as code paths are exercised — bounded, not a leak. `RssFile` sat at a
constant `257880 kB` across every sample.

## The sample-to-sample growth was the lock screen

Two consecutive samples showed RSS rising 8.7 MB while `RssAnon` rose 0.8 MB and
`RssFile` did not move — arithmetic that did not close, because the v1 sampler
did not log `RssShmem`. It was an 8 MB `/dev/shm/swaylock-*` buffer: **the lock
surface, mapped by the compositor while the screen was locked.**

Proven by unlocking:

| | locked | unlocked |
|---|---|---|
| swaylock processes | 2 | 0 |
| `/dev/shm/swaylock-*` files | 2 | 0 |
| mapped by niri | 2 | 0 |
| **`RssShmem`** | **8172 kB** | **12 kB** |

**Fully reclaimed.** Transient, correct behaviour.

*(Incidental: the lock happened because the old 300 s swayidle was still running
during the sampler work and fired. Worth noting that `swaylock` was deliberately
**not** killed to investigate — under `ext_session_lock_v1` the compositor keeps
the screen locked if the lock client dies, so killing it can strand the machine.)*

## The finding that does matter: 90 MB of NVIDIA libraries doing nothing

`libnvidia-gpucomp` (69 MB) + `libnvidia-eglcore` (21 MB) are mapped, NVIDIA
device nodes are open, and an NVIDIA `GLCache` has been written — **while every
frame is rendered on Intel.** `/proc/<niri>/fdinfo` reports `driver=i915` with
**10.8 s of `drm-engine-render`** and every NVIDIA engine at **0 ns**.

This is the glvnd behaviour the `browser` row documented — every vendor in
`/usr/share/glvnd/egl_vendor.d/` gets dlopened during EGL init — **at three times
the scale** (90 MB here versus 32.9 MB for Brave).

**It is a hybrid-laptop artifact, not a BunnE cost.** On the NVIDIA-only daily
driver those libraries do the actual work. **So `bunne-test` systematically
overstates compositor memory for the real target**, and niri's figure should be
re-measured on the desktop in Phase 6 before it is treated as a budget problem.

## Conclusion

**No action needed.** niri's heap is 30 MB; the rest is a graphics stack that any
compositor on this hardware would map, roughly a third of it an artifact of
hybrid graphics that will not exist on the target machine.
