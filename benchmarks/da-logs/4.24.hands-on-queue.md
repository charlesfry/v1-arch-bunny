## The findings that changed something

**A — the load-bearing sentence was false.** The write-up said `pacman -Rs` "only takes
dependencies nothing else needs, so the removal set is the package manager's own answer,
not an opinion." `man pacman` on this machine: removal is skipped only where a package is
required by others **or explicitly installed** — *hard depends only*. Optdepends are
invisible; several removals here are optdepends of installed packages (`libdecor` of
`gtk3`, `xorg-xwayland` of `wlroots`). DA's phrasing: it "launders an untested claim into
'the tool decided'". Also: nothing was launched, and "complete" was never measured, since
`-Rs` leaves anything explicitly installed (a `pacman -Qe` diff would settle it).

**B — two control-void claims, both flattering.** Idle power was two single samples from
different sessions, boots and post-boot ages, called "within noise" with the noise never
measured. The boot "before/after" was almost certainly one `systemd-analyze` output read
as two runs — it prints the userspace figure and the `graphical.target` figure together —
and the metric cannot test a module-packaging change anyway, since both routes yield the
same `.ko` loaded in the initramfs phase. DA also caught the one-sided ledger: the
prebuilt module is path-pinned to one kernel version, which *moves* a failure mode rather
than removing it, and interacts with booting an older snapshot's kernel.

**C — validated in the one state where the hazard cannot occur.** `docker images` was
empty, so the migration never met the thing that breaks it: `btrfs subvolume snapshot`
does not recurse into nested subvolumes and docker's btrfs driver makes one per layer.
The instrument handled this with a *comment* and no runtime guard — DA: "run on a
populated machine it produces a `@dockervol` that looks migrated and is missing every
layer." Guard added. Separately: cap proven for `@dockervol` only, at a synthetic 8 MiB,
through `dd` not docker; and **the rollback isolation the whole change exists for is
unexercised**, which the repo's own rule calls broken until demonstrated. DA also noted
the unit nobody had stated — a qgroup limit counts *compressed on-disk* bytes.

**D — the test could not have failed visibly.** DA decoded the deposited proof PNG: the
image satty holds is a **flat RGB(15,15,15) field, zero distinct values across ~43,000
sampled pixels**, and the desktop background around it is the same colour. Wrong region,
wrong stride, wrong pixel format, half-drawn frame — all identical to a pass. The one bit
it does carry is that the field is `0f0f0f`, not `000000`, so not a zeroed buffer. Plus:
the command tested (`-g "0,0 640x400" … --output-filename`) is not the command bound
(`-g "$(slurp)"`), and `slurp`'s cancel path — the common gesture — fails silently inside
`spawn-sh`.

**E — the one that survives.** Mechanism explained, demonstrated both directions,
corroborated by an IPC spawn succeeding on a session `-f` called "locked". DA added two
caveats now recorded: `pgrep -x` is name-exact and would answer "unlocked" for a
different locker, and the box's 28800 s test-rig idle timeout means the run says nothing
about the shipped config's locking.

**F — the mechanism was inferred from a document that does not state it.** DA read
`CONFIG.md` end to end and found nothing supporting "a directory as default entry does
not boot", plus an internal inconsistency on the neighbouring sentence (*"the timeout in
seconds before the **first** entry is automatically booted… If set to `0`, boots
**default** entry instantly"*). Its point stands on the project's own rule: limine is
open source and **the read did not need the test box**.

Done in response, and it changed the recovery advice:

- `common/menu.c` (v12.5.2) line 1962 — `if (max_entries == 0 || selected_menu_entry->sub
  != NULL) skip_timeout = true;`. A directory as the selected entry **forces the timeout
  off**; the menu waits indefinitely. Proven, not inferred.
- The `autoboot:` label — a directory toggles `expanded` and refreshes. **Enter on a
  folder never boots.** So recovery is three keys, not the "one keypress" first written.
- `print_tree()` counts children **only when the directory is expanded** — so `+` is
  load-bearing for a numeric `default_entry`, and `default_entry: 2` *without* it is out
  of range. The two-part repair first recommended had a half whose omission is a
  different failure.
- `find_entry_by_path()` expands as it walks and matches only leaves — so the **path
  form** cannot select a folder and cannot be renumbered. `default_entry: Arch
  Linux/linux` is the one-line repair, and is now what the docs and the check recommend.

DA also supplied a competing hypothesis from the same reference the write-up claimed to
have consulted: **`hash_mismatch_panic` defaults to panic**, the desktop config sets it to
`no`, `bunne-test` does not, and the hook hashes every ESP path. A stale hash panics
rather than showing a menu — different symptom, different fix. Recorded in
`snapshot-boot-entries`. DA's remaining point stands: **the box's state is still a ranked
hypothesis, because nobody has seen the screen.**

**G — the check emitted false assurance, which is worse than no check.** DA ran it:
a non-numeric `default_entry` skipped check 1 wholesale and the script printed
*"default_entry Arch Linux/linux is bootable"* anyway; a bogus path was not flagged; and
any `path:` not using `boot():` — the desktop config has one — was silently skipped while
the same line claimed "all booted files present". Rewritten: the pass line now enumerates
what was checked *and what it skipped*, the collapsed-directory case is a FAIL rather than
a cosmetic WARN, and `--self-test` covers three near-misses instead of one shape. DA also
did work the packet had not: it corroborated the indexing model from `/proc/cmdline` and
`findmnt /` on the desktop, ruling out both competing schemes.
