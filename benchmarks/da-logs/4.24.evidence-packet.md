## Conclusion F — why the box is now unreachable (THE WEAKEST CLAIM; ATTACK THIS)

**Claim:** `bunne-test` is sitting at the Limine boot menu because
`/boot/limine.conf` was restructured so that `/Arch Linux` became a directory,
while `default_entry` remained unset and therefore defaults to `1` — and entry 1
is that directory, which is not bootable.

**What is actually known:**
- The config before the edit (produced by `limine-mkinitcpio-hook`) kept the
  original hand-written boot options on `/Arch Linux` *and* added a `//linux`
  child. The machine booted fine from it. That boot was verified.
- The edit removed those four option lines from `/Arch Linux`, added
  `comment: machine-id=…`, and left everything else alone. `limine-update` was
  re-run and preserved the shape. `limine-list` printed:
  ```
  Arch Linux
  ├─ linux
  └─ Snapshots
     └─ 77 │ 2026-08-25 17:28:39
  ```
- `sudo efibootmgr --bootnext 0001` (the `Limine` entry) was set, `BootOrder` was
  restored to NixOS-first, and the machine was rebooted.
- The machine has not answered ping or ssh since, ~45 minutes and counting.
  Before this reboot, four reboots the same evening each came back within ~60-90 s.
- NixOS lives on a **separate ESP** with its own `Boot0007` and is unaffected by
  anything in the Arch `limine.conf`.

**What supports the diagnosis:**
- `limine` `CONFIG.md`, read on the machine: *"`default_entry` — Entry which will
  be automatically selected at startup. Can be a 1-based entry index … If
  unspecified, it is `1`."* and *"A menu entry can be a directory… In order for an
  entry to become a directory, it needs to have a sub-entry following right after
  it."*
- The author's own Omarchy desktop runs the same two packages with a working
  config whose head is `timeout: 60` / `default_entry: 2` and whose OS entry is
  `/+Omarchy` — i.e. the default points at the *child*, and the directory is
  expanded. The edited bunne-test config had neither.

**What is NOT known, and cannot be checked while the box is down:**
- Nobody has seen the screen. There is no direct evidence of a menu.
- No serial console, no IPMI, no photo.
- Alternative explanations not excluded: a LUKS passphrase prompt (the box
  normally auto-unlocks from an initramfs keyfile per the `benchmark-unlock` row,
  and the initramfs was rebuilt twice this evening — once by the `nvidia-open`
  transaction, once by `limine-update`); a firmware/UEFI failure to launch
  `Boot0001` at all; a hardware or network fault coincident with the reboot; the
  machine having powered off.
- The claim "one keypress fixes it" is entirely untested.

## Conclusion G — `scripts/check-limine.sh` catches the failure class

**Claim:** the new check FAILs the configuration described in F, passes its
two-line repair, and passes the author's real working `limine.conf` with no false
warnings.

**Raw:**
```
$ ./scripts/check-limine.sh /boot/limine.conf          # the desktop's working config
ok: /boot/limine.conf — default_entry 2 is bootable, all booted files present
rc=0

$ ESP=<fixture> ./scripts/check-limine.sh broken-limine.conf
FAIL: … default_entry 1 is "Arch Linux", a DIRECTORY.
    A directory is not bootable: limine will show the menu and wait forever.
    Point default_entry at the kernel child instead (usually 2).
rc=1

$ ESP=<fixture> ./scripts/check-limine.sh fixed-limine.conf
ok: … default_entry 2 is bootable, all booted files present
rc=0

$ ./scripts/check-limine.sh --self-test
self-test ok: rejects the 2026-08-25 config, accepts its repair

$ <copy with check 1 sabotaged to `elif false`> --self-test
SELF-TEST FAIL: a directory as default_entry was accepted
rc=1
```

**Assumption embedded in the script, worth attacking:** that `default_entry`
indexes *every* entry depth-first including children, not just top-level entries.
This was inferred from the desktop config (`default_entry: 2` with `/+Omarchy`
first boots Omarchy's `//linux` child, and that machine does boot Omarchy by
default) — **not** from limine's source, and not from any statement in `CONFIG.md`,
which says only "1-based entry index". An earlier version of the script assumed
top-level-only indexing and produced a *false pass* on the desktop config for the
wrong reason.

**Not done:** the check has never been run against `bunne-test`'s own
`limine.conf`. It has been run against exactly one real-world config.
