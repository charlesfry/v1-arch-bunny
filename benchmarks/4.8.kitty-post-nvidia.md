# 4.8 — does the NVIDIA driver change kitty launch? (author's hypothesis)

`arch-bunny`, 2026-08-24. Author's hypothesis, verbatim: "modern GPU drivers
may speed up cold kitty launches. i suspect the slow kitty launch (~177ms)
is due to it needing the GPU."

Context: `nvidia-open-dkms` 610.57.04 was installed today (author's
decision, `CHOICES.md` `gpu-driver`), replacing firmware-less nouveau on the
otherwise-unused dGPU. The panel kitty renders on is Intel (i915) either
way. Two prior mechanisms cut opposite directions: removing nouveau's broken
state could speed anything that probed it; adding an nvidia EGL ICD gives
glvnd one more vendor library to dlopen at EGL init (session 6 measured
33 MB of nvidia libraries mapped into Brave's GPU process on this hybrid
box for exactly that reason).

## Pre-registered before results (written while the runs were in flight)

Baseline, same instrument (`instruments/spawnbench.py` v2), same install,
same kernel (7.1.9-arch1-2), 2026-08-23 night, pre-nvidia, 4 boots:

- kitty cold (run 0 of boot): **169.5 / 173.8 / 180.7 / 188.2 ms**
- kitty warm median: **128.5 / 130.1 / 130.2 / 131.7 ms**
- fuzzel (control) warm median: **20.9 – 21.8 ms**

> warm envelope above laundered one **zen-kernel** boot (128.5 is
> `battery.arch-zen-boot2.log`) into a "same kernel" baseline, and
> fuzzel's 21.8 is also zen. The correct mainline-only envelopes:
> **kitty warm median 130.1–131.7**, **fuzzel 20.9–21.5**. Colds were
> correct as stated. The error biased *against* the eventual claim
> (a wider envelope makes a slowdown harder to show), which saves the
> direction, not the transcription.

Tonight: 3 fresh boots (the first boot after the install's initramfs
regeneration discarded per the 3.3 rule), n=10 per app per boot, same
invocation (`spawnbench.py 10 kitty,fuzzel`).

Decision rule:
- **Supported** — all 3 new colds below 169.5 ms AND their median >10%
  below the baseline cold median (~177 ms), with fuzzel unmoved.
- **Refuted, opposite sign** — all 3 new colds above 188.2 ms (the new EGL
  ICD costs more than broken nouveau did), fuzzel unmoved.
- **Null** — new colds overlap the 169.5–188.2 envelope.
- Any fuzzel shift outside ~20.9–21.8 median voids the comparison (boot
  environment changed, not kitty).
- Mechanism probe: a live kitty's `/proc/<pid>/maps` grepped for nvidia
  libraries. Zero nvidia mappings + a timing shift = flagged as
  mechanism-free; mappings present give the glvnd path a paper trail.

Every kitty cold is above the entire pre-nvidia envelope (169.5-188.2);

## Mechanism (same boot, boot 3, load ≤0.25)

- A live kitty spawned via the session (niri IPC) maps **47 nvidia
  entries**: `libEGL_nvidia`, `libnvidia-eglcore`, `libnvidia-glsi`,
  `libnvidia-gpucomp`, plus 5 EGL platform shims — glvnd enumerates every
  installed vendor ICD at EGL init.
- **A/B with only the ICD pinned** (`__EGL_VENDOR_LIBRARY_FILENAMES=
  .../50_mesa.json`): warm median **131.8 ms** vs the same boot's default
  **142.5 ms** — mesa-pinned lands exactly in the pre-nvidia envelope.
  Boot environment held fixed; only glvnd's vendor list differs.
- PSS, same boot, same method (`smaps_rollup`, single kitty window):
  default **181.2 MB**, mesa-pinned **137.9 MB** → the nvidia stack costs
  **+43.3 MB PSS** on a solo kitty. (4.3's "75.3 MB" does not reconcile
  with either number and that cross-night comparison is NOT same-method
  verified — do not quote a "+106 MB" delta.)
- **fuzzel maps zero EGL/nvidia libraries** (software-rendered), so its
  +1 ms is not in its own process. niri itself now holds the nvidia DRM
  device open and maps 73 nvidia entries — the plausible compositor-side
  route; **left open, unattributed** (small, consistent direction, n=3).

## Verdict after DA round 1 (rejected as first stated — see `da-logs/4.8.kitty-post-nvidia.md`)

DA round 1 rejected the original "refuted with sign reversed" headline:
the pre-registered rule actually fired **VOID** (the control moved, and
the rule had no cross-boot-only scoping), the mechanism A/B was post-hoc
and its raw data never deposited, the cold claim rested entirely on the
voided cross-boot comparison, and the baseline was zen-contaminated (fixed
above). **What survives round 1:** "hypothesis not supported" (a +1 ms
control shift cannot mask the hypothesized ~18 ms cold speedup), and the
default-arm warm shift as the strongest on-file fact (142.5/142.7/142.5
vs mainline 130.1-131.7, tight distributions, 3 boots).

## 4.8b results (raw: `raw/4.8b.kitty-ab.jsonl`, deposited verbatim)

Two boots, distinct boot ids in the raw (`e9dbf47e…`, `1816b6a3…`), same
kernel/driver, 60 s settle matching the baseline harness.

| boot | block order | default warm medians | mesa warm medians | Δ per adjacent pair |
|---|---|---|---|---|
| A | D M D M | 141.8 / 140.0 | 132.2 / 131.9 | **9.6 / 8.1** |
| B | M D M D | 142.6 / 140.8 | 132.4 / 133.7 | **10.2 / 7.1** |

Maps, per boot: default kitty **47 nvidia entries** (9 distinct libs, named
in raw), mesa kitty **0**, fuzzel **0**. Boot-colds, the pre-registered n=1
directional pair: default 191.1 (boot A) vs mesa 177.1 (boot B) —
consistent direction, **no claim entered**, as pre-registered.

**Pre-registered rule: fires on every condition, both boots.** Δ ≥ 5 ms in
all four block pairs (7.1–10.2 ms); mesa arm within 3 ms of the corrected
mainline envelope; default maps nvidia, mesa maps none.

Honesty notes per DA round 2: (i) warm n is **8/arm/boot**, not 10 — the
instrument labels run 0 of *every* block cold, so mid-boot block-starts
are excluded; both arms treated identically, and the warm distributions
are essentially disjoint regardless. (ii) One mesa warm outlier (166.3,
boot B first mesa block) shows the cold tail extends past run 0 — so the
n=1 "boot-cold" pair sits on a warmup curve, another reason it stays a
non-claim. (iii) The envelope condition is itself a cross-night comparison
and is **degraded by the moved fuzzel control** (22.7/22.2 vs 20.9–21.5,
now shifted in 5/5 post-nvidia boots vs 4/4 pre) — survivable only because
a ~1 ms environment shift cannot manufacture a 7–10 ms within-boot delta.
The fuzzel shift is hereby promoted from curiosity to open question:
fuzzel maps zero EGL/nvidia libs, so the named suspect is compositor-side
(niri maps 73 nvidia entries and holds the nvidia DRM device); every
future cross-night envelope inherits this until probed. (iv) The
pre-registration commit preceded boot A by 38 s on two machines' clocks
(journal excerpts deposited in raw settle the boot timeline itself);
future pre-registrations get minutes of margin, not seconds. (v) Power
state now deposited (AC online); the pre-nvidia baseline logs don't state
theirs — `battery.*` in those filenames means a battery *of tests*, but
the power-state asymmetry is formally unverified.

**PSS — corrected per DA round 2, which caught a false retraction.** The
first draft of this section claimed the mesa-arm PSS "failed to deposit"
and attributed no RAM cost. Wrong twice: the probe's quoting bug only
*split the line* (a `grep -c` no-match printed a second `0` before
`pss_kb=`), and the mesa readings were in the raw all along —
**72,790 / 72,683 kB**, agreeing within 107 kB across two boots. The
deposited within-boot, same-method pairs at ~130 s uptime are therefore
default **138.0 / 138.7 MB** vs mesa **72.8 / 72.7 MB**: a **+65–66 MB**
nvidia-attributable delta, replicated. The impeached number was
yesterday's *undeposited* "mesa 137.9" (round 1 criticism #1 already
disqualified that pair) — the first retraction trusted the disqualified
data over the deposited data.

**Addendum probe (same boot B, 651 s uptime, pid+cmdline deposited, AC
power deposited):** default **262.6 / 262.8 MB** (47 nvidia maps), mesa
**171.5 / 171.6 MB** (0 maps) — delta **+91.1 / +91.2 MB**. So:

- The nvidia EGL stack adds a **large, replicated, within-timepoint PSS
  cost** to any kitty that maps it: +65–66 MB early in a session, +91 MB
  later in the same boot.
- **No absolute solo-kitty PSS is quotable on this box**: the mesa arm
  alone went 72.7 → 171.5 MB within one boot as the session aged. Every
  historical absolute (4.3's 75.3, the undeposited 181.2/137.9) is
  method-unanchored. A steady-state PSS method (fixed window age, fixed
  spawn history, stated uptime) must be settled before any `BUDGET.md`
  row quotes a kitty RAM figure — the "+43.3 MB" and "no RAM cost"
  claims are both dead.

Consequences:

1. **Bake-off confound found**: 4.2's kitty rows compared Arch *without*
   nvidia against NixOS *with* nvidia(-open). No re-quoted gap number is
   entered (DA r1 #8): tonight's Arch numbers vs last night's NixOS is a
   cross-night comparison, and whether NixOS's kitty even pays the same
   ICD tax is unverified (its `/run/opengl-driver` glvnd plumbing differs
   from Arch's `/usr/share/glvnd`; needs a NixOS-side kitty maps dump).
   The honest statement: the ~23 ms gap in 4.2 is partly or wholly a
   driver-stack asymmetry, size unresolved until measured symmetrically.
   Annotated in 4.2.
2. **Author decision spawned** (laptop only): pin kitty's launch keybind to
   the mesa ICD (`__EGL_VENDOR_LIBRARY_FILENAMES`) and buy back **~7–10 ms
   per warm launch** plus a real-but-unquantified PSS cost (deposited
   within-boot deltas +65–91 MB depending on session age; method
   unsettled)? Costs: a config line that must NOT ship to the NVIDIA-only
   desktop, where the nvidia ICD is the one doing the work and its cost is
   intrinsic. This is the same hybrid-laptop artifact class as session 6's
   Brave finding (33 MB of nvidia libs in a GPU process driving nothing).
3. The 2a target readout changes: "130 ms is kitty's intrinsic floor" (4.3)
   was true of the *driverless-dGPU* laptop; on any machine with the nvidia
   ICD installed, the floor includes the glvnd tax unless pinned.
