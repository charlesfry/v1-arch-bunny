# 4.18 — oom-protection and load-protection: both mechanisms exercised (overnight, 2026-08-25)

Two deferred rows, one session, both tested with canary-shaped protocols on
`arch-bunny` (fresh boot, idle, load 0.0). Instruments:
`instruments/4.18-{oomd,loadprot}.sh`; raw: `raw/4.18.{oomd,loadprot}.log`.

## load-protection: CPUWeight alone is HALF an answer; + core reservation is the whole one

Question (the row's premise): does a CPUWeight-capped hog keep interactive
latency near baseline during a "training run"? Instrument: spawnbench kitty
spawn→window-mapped, n=5 warm per condition, same session.

| condition | kitty warm median |
|---|---|
| A — idle baseline | **141.6 ms** |
| B — 12-spinner hog, default weight (100) | **504.2 ms** (3.6×) |
| C — same hog, `CPUWeight=1` | **330.5 ms** (2.3×) |
| D — hog `CPUWeight=1` + `AllowedCPUs=0,1,6,7` (2 physical cores; siblings verified (0,6),(1,7)) | **149.2 ms (≈ baseline)** |

Mechanism decomposition, each step verified rather than assumed: the cpu
controller is genuinely delegated at every level down to `user@.service`
(`cgroup.subtree_control` read) and the hog's effective `cpu.weight` was 1;
all-core frequency under load drops only 4.29→3.99 GHz (~7% — nowhere near
2.3×); the residual after weighting is therefore **indicated as SMT sibling
pollution**. *DA round 15 correction:* condition D changed **two**
variables at once — cores restricted AND spinner count reduced (4, not 12)
— so C→D does not isolate SMT from runqueue relief; the **recipe claim
stands as run** (weight + reserved whole cores ⇒ baseline latency), the
mechanism split is indicated (clocks ruled out), not isolated. A clean D′
(12 spinners confined to 4 CPUs) would settle it if the number ever
matters.

**Row-ready recipe** (for the author): weights alone ≈ halve the inflation;
the full protection for a saturating training run is
`systemd-run -p CPUWeight=<low> -p AllowedCPUs=<all-but-N-cores>` (or the
equivalent slice config), reserving a core or two for the session. Zero
packages, zero resident cost — pure systemd. Caveats: single session, n=5
per condition, one hog shape (pure CPU spin); IO-heavy load untested.

## oom-protection: systemd-oomd kills the right thing before the kernel does — PASS

Test-rig config applied (recorded; left enabled as a soak): systemd-oomd
enabled; drop-ins `ManagedOOMSwap=kill` on `-.slice` and
`ManagedOOMSwap=kill` + `ManagedOOMMemoryPressure=kill` on `user@.service`.
Canary: a transient user unit allocating **incompressible** 256 MiB
`os.urandom` chunks (zram compresses zero-pages to nothing — a naive hog
never fills swap), `RuntimeMaxSec=300` as the fail-loudly backstop (hog
dying by timeout = mechanism did nothing).

Result, from the journal: at RAM 16.3/16.6 GB and swap 7.5/8.3 GB (>90%),
`systemd-oomd` **marked exactly the hog's cgroup**
(`.../app.slice/t-memhog.service`, top swap candidate at 7.3 G) and killed
it (SIGKILL, unit `Failed with result 'oom-kill'`, peak 13.7 G RAM +
7.3 G swap). Recovery was instant (swap back to 15 MiB within the next 5 s
poll). **The kernel OOM killer never fired** (dmesg swept: no
`Out of memory`/`oom-kill` lines). **The box never
meaningfully stalled**: the 5 s responsiveness loop ticked t+5 through
t+56 with no multi-second stretch — one interval ran 6 s (t+45→t+51,
≤1 s stall at peak pressure), disclosed per DA round 15.

Disclosures: (1) the **swap-kill path** is what fired; the pressure path
(`ManagedOOMMemoryPressure`) is configured but was never exercised — the
ramp was too fast to accumulate sustained PSI; a slow-leak-shaped canary
would test it. (2) Instrument bug, evidence unaffected: `--collect` reaped
the failed unit before the script's `Result` query, so the script's own
VERDICT line misprints `success`; the journal (`oom-kill`) is the record.
(3) One hog shape, one run; 16 GB/zram-only box — thresholds scale
differently on the 64 GB target, the mechanism transfers. (4) oomd's
resident cost on this box: one daemon (~1-2 MB class) — measure PSS before
the row ships it.

**Both rows now have what they lacked — an exercised mechanism.** Decisions
stay the author's; drafts for the two rows go in the morning report.
