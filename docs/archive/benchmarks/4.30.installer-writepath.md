# 4.30 — breaking every step at once, and one `install.sh` putting it back

**2026-08-26. `bunne-test`, kernel 7.1.9-arch1-2.** The installer now has nine steps and
each one has been broken and re-run *individually* while it was being written — that is the
method that found every defect so far. What had never been tested is **all of them at once**,
which is the only shape that can surface an ordering problem: a step that appears to work
only because a later step had already run, or because some state a previous session left
behind was quietly load-bearing.

Instrument: `benchmarks/instruments/p4-installer-writepath.sh`.

## The headline

**A machine deliberately broken across every step was repaired by one `install.sh` run, exit
0, and came back from a cold boot with zero failed units.** No step depended on state a
later step provides. Nothing needed a second run.

## Method

The instrument breaks, in one pass, every state the installer is supposed to create:

| step | how it was broken |
|---|---|
| `15-docker-subvols` | both subvolumes unmounted, both fstab lines deleted, `/var/lib/docker` chmod'd to 755 |
| `30-zram` | `zram-size = 128`, `99-zram.conf` deleted, both sysctls set live to the kernel defaults |
| `35-oom-protection` | both drop-ins deleted, `systemd-oomd` disabled and stopped |
| `40-snapshots` | all five values set back to snapper's template defaults, `snapper-timeline.timer` **enabled** |
| `60-autologin` | drop-in directory deleted, the `exec niri-session` block cut out of `~/.bash_profile` |
| `70-dotfiles` | one link replaced by an *identical* regular file, one by a *divergent* one, one deleted outright |

Three things were left alone on purpose, and the reasons are as much a part of the design as
the breakages: **packages** (removing and reinstalling 75 of them tests pacman, not us),
**`/boot`** (`50-limine.sh` was proven by a real reboot in an earlier session, and breaking a
bootloader on a box with no remote power control buys nothing), and the **LUKS keyfile plus
the test-box sudoers file**, which are what make this machine drivable headless at all.

## Result

One `./install.sh`, exit 0. Every step reported `+` lines rather than `=`, which is the
point — this is the first run in which the *changing* code path executed end to end. The
three dotfile shapes each behaved as designed: the identical copy was relinked silently, the
divergent one was kept as `kitty.conf.bunne.bak`, the missing one was recreated.

Then a cold boot, checked at 92 s of uptime:

```
failed units: []
root:       subvol=/@
docker:     /dev/mapper/cryptroot[/@dockervol]     mode 710
containerd: /dev/mapper/cryptroot[/@containerd]    mode 700
zram:       /dev/zram0 7.7G
sysctls:    swappiness=180 page-cluster=0
oomd:       active / pressure-monitored=1
timeline:   disabled
snapper:    SPACE_LIMIT=0.08
session:    niri, waybar, logged in on tty1
links:      6/6 symlinks into the repo
images:     python:3.12-slim
```

## What the run found

**Nothing in the installer — and one bug in the instrument, which is worth more than it
sounds.** The first version chmod'd `/var/lib/docker` to 755 *after* unmounting it, so it
changed the mountpoint underneath rather than the mounted subvolume root. The next mount
hides that, so the break silently did nothing and `15-docker-subvols`' mode check was never
exercised. Reordered to chmod before the unmount, the step then correctly reported
`+ /var/lib/docker mode 0710`.

That is the same mechanism as the real defect this check exists for — a mode applied to a
mountpoint disappears under the mount — showing up a second time, now in the test rather
than in the code. **A test that cannot fail is indistinguishable from a test that passes**,
and the only thing separating the two here was checking that the break actually took.

## Scope, stated honestly

This proves the write paths run correctly **in sequence on a machine that was already
provisioned once**. It is not a fresh-install test: the subvolumes still existed (only their
mounts and fstab lines were removed), the packages were all present, and `/boot` was
untouched. The genuine unknown remains a run against a machine straight out of
`archinstall`, which cannot happen until `bunne-test` is wiped in Phase 5.
