# Phase 3 — shell latency: per-login, per-terminal, per-prompt

> ### ⚠ Measurement caveat — the desktop is not a quiet machine
>
> Added 2026-08-21 at the author's prompting, and **verified**: the Omarchy
> desktop is his working machine and runs CPU-heavy ML training while this hobby
> project is being worked on. At the time these numbers were taken it showed
> **load average 32.5 on 24 cores**, with four `python3` processes at ~600% CPU
> each. Every desktop figure here is inflated.
>
> **Measured inflation**, same primitives on the idle laptop:
>
> | primitive | desktop (load 32.5) | idle laptop | ratio |
> |---|---|---|---|
> | bash function call | 0.201 ms | 0.089 ms | 2.3x |
> | one `$( )` subshell | 2.977 ms | 1.023 ms | 2.9x |
> | one `$( /bin/true )` fork | 5.298 ms | 2.103 ms | 2.5x |
>
> **The inflation is roughly uniform (2.3-2.9x), so relative comparisons and
> every conclusion drawn from them survive; the absolute numbers do not.** Divide
> desktop figures by ~2.5 for an unloaded estimate. Note this bias *flatters* the
> fork-free recommendations, since forking suffers more under contention than
> pure-bash work does — which is the case for reading them sceptically, not
> credulously. A second confound: the laptop's environment is 406 bytes / 17 vars
> against the desktop's 9950 / 226, and subshell cost scales with environment
> size, so a lean BunnE gets cheaper subshells for free.
>
> **Rule going forward: record `uptime` alongside any timing taken on the
> desktop, and prefer the laptop for absolute numbers.**


Measured 2026-08-21 on both machines. The project's first priority-2a results.
None of this costs a byte at idle, which is why none of it had ever been seen.

**Read the tiers separately.** A cost paid once per login and a cost paid on every
prompt are not comparable, and conflating them was the first mistake here.

| Tier | Paid when | Desktop | `bunne-test` |
|---|---|---|---|
| `/etc/profile` | **once per session login** | 571.4 ms | 75.2 ms |
| `~/.bashrc` | **every new terminal** | 272.4 ms | 3.4 ms (bare) |
| `starship prompt` | **every prompt** | 33.8 ms in a git repo | not installed |

Baseline: bare `bash --noprofile --norc` is 5.4 ms (desktop) / 1.6 ms (laptop).

## Correction: `/etc/profile` is per-login, not per-terminal

An earlier draft of this file implied the 460 ms `vapoursynth.sh` cost was paid
on every terminal. **It is not**, and the difference matters enough to state
plainly.

Checked on the running Omarchy desktop: alacritty's shell children have
`argv[0] == /usr/bin/bash`, with **no leading hyphen**, so they are *interactive
non-login* shells and never read `/etc/profile`. The session inherits
`VSSCRIPT_PATH` and `DEBUGINFOD_URLS` from the login that started it — both are
present in alacritty's own environment — so the cost is paid **once**, at session
start, and inherited thereafter.

**Nor does BunnE's terminal pick change this.** From kitty's own source,
`kitty/child.py`:

```python
self.should_run_via_run_shell_kitten = is_macos and self.is_default_shell
```

The login-shell `-` prefix is gated on **macOS only**, and kitty's comment says
so explicitly: *"it is arguable whether graphical terminals should start shells
in login mode in general... xterm, urxvt, konsole and gnome-terminal do not do it
in my testing."* So alacritty → kitty introduces **no regression here**.

`/etc/profile` still costs 571 ms of the `power-on → usable desktop` path, which
`02-functionality.md` C2 names. It is worth fixing. It is not an emergency.

## Tier 1 — `/etc/profile`, per login

| Script | `bunne-test` | desktop |
|---|---|---|
| **`vapoursynth.sh`** | **63.8 ms** | **460.1 ms** |
| `flatpak.sh` | — | 59.4 ms |
| `debuginfod.sh` | 12.4 ms | 13.2 ms |
| `gpm.sh` / `perlbin.sh` / `80-systemd-osc-context.sh` | ~5 ms | ~16 ms total |

The whole of `/etc/profile.d/vapoursynth.sh` is 49 bytes:

```sh
export VSSCRIPT_PATH=$(vapoursynth get-vsscript)
```

It forks a Python-backed binary to print a constant path. **It costs more on the
better machine** — 460 ms on the 12-core desktop vs 64 ms on the fresh laptop —
because the desktop has more `site-packages` to walk. It gets worse the more the
machine is used for data science.

**Decision: do nothing here.** `CHOICES.md` `shell-startup` is `rejected`. The
`NoExtract = etc/profile.d/vapoursynth.sh` fix works and was tested, but it hides
a file inside a package that still claims to own it, and a fresh BunnE install
pays only **64 ms** — the 460 ms is what years of `site-packages` growth does to
the *oldest* machine. ~25 s/year against a permanent system-wide hack that would
mislead the next person to debug it. **The right fix is an Arch bug report**: a
`profile.d` script forking a Python interpreter to print a constant is a
packaging defect, and fixing it upstream helps everyone.

**ffmpeg is not the culprit and is not really a choice.** `vapoursynth` is
`Required By: ffmpeg mpv`, and ffmpeg is unavoidable: mpv is the picked video
player, and on `bunne-test` ffmpeg arrived through an entirely different route
already documented in `CHOICES.md` `portal` (portal → nautilus → localsearch →
ffmpeg). Rebuilding ffmpeg from the AUR to drop a `--enable-vapoursynth` flag
would mean owning a large, frequently-updated build to delete one 49-byte file.
**Delete the file instead** — see `CHOICES.md` `shell-startup`.

## Tier 2 — `~/.bashrc`, every new terminal

Desktop total **272.4 ms**. Components, each measured as a delta over bare bash:

| Component | Cost |
|---|---|
| `omarchy default/bash/rc` (contains most of the below) | 229.8 ms |
| └ `mise activate bash` | **117.1 ms** |
| └ `starship init bash` | 45.5 ms |
| └ `direnv hook bash` | 15.1 ms |
| `conda.sh` (miniforge) | **0.3 ms** |

**`conda.sh` is the model to copy, not the villain.** It costs 0.3 ms because it
only *defines a function*; the expensive part — `conda shell.bash hook`, measured
at **2341 ms** — is deferred until `conda activate` actually runs. Every other
integration here does its expensive work eagerly at shell start.

**`mise activate` at 117 ms is the single largest per-terminal item**, paid on
every terminal to manage a node version. `mise` is listed in `03-alternatives.md`
under "keep as-is, all cheap and all in use". That characterisation is now
measured and wrong.

## Tier 3 — `starship`, every prompt

| Context | Cost |
|---|---|
| inside a git repo | **33.8 ms** |
| outside one (`/tmp`) | 14.0 ms |
| (`git status --porcelain` alone, same repo) | 14.3 ms |

`03-alternatives.md` asked for this number — *"Measure its per-prompt cost with
`hyperfine` first — it forks"* — and it is the most-repeated latency on the
machine: paid after **every command**, in the directory type the author is almost
always in. `01-assessment.md` counts `git` 3897 times in shell history.

The git-repo penalty is ~20 ms over the non-git case, and a bare
`git status --porcelain` accounts for 14.3 ms of it, so most of the difference is
starship shelling out to git rather than starship itself being slow.

`03-alternatives.md` ranks a hand-rolled `PS1` as candidate 2 "if starship
measures badly". **It now has a number to be judged against.**

## Where the time actually is

Ranked by annual cost, assuming one login, ~20 terminals and ~200 prompts a day:

| Cost | Per year | Whose file | Needs a hack? |
|---|---|---|---|
| `starship` per prompt | **~40 min** | ours | no |
| `mise activate` per terminal | ~14 min | ours | no |
| `vapoursynth` per login (fresh machine) | ~25 s | Arch's | yes |

**The dramatic finding is the least valuable one, and the only one that demanded
cleverness.** The two that cost real time sit in config files BunnE writes from
scratch, where the fix is simply not doing the slow thing.

## What this changes for Phase 4

1. **Port the shell config by measurement, not by copying.** The three eager
   integrations (`mise`, `starship`, `direnv`) cost 178 ms of the 272 ms.
2. **Prefer the `conda.sh` pattern** — define a function, defer the fork — for
   anything that must exist in `.bashrc` at all.
3. **`/etc/profile.d` is an unaudited latency surface.** No package list reveals
   it; the offender arrived three dependencies below a video player. The
   installer should enumerate and time it as a build step.
4. **Measure per-prompt separately from per-shell.** A 34 ms prompt is worse than
   a 272 ms shell start for anyone who runs more than eight commands per terminal.
