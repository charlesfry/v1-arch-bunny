# Phase 3 — why `gr` is slow, taken apart layer by layer

`bunne-test`, 2026-08-21, **idle**. Servers installed into a throwaway venv
(no root available). Two real projects, not synthetic:

| project | py files | lines | ground-truth occurrences of the symbol |
|---|---|---|---|
| `rich` | 213 | 51,866 | 757 (`Console`, word-boundary) |
| `pandas` | 1,560 | 702,121 | 19,876 (`DataFrame`) |

Measured with `~/t-lspref.lua`, which issues `textDocument/references`
**with no picker in the way** — the whole point is to find out which layer
costs what.

## Layer 1 — the language server, and a correctness problem

`rich`, cursor on `class Console`:

| server | attach | 1st call | warm | **refs returned** |
|---|---|---|---|---|
| basedpyright | 226 ms | 1159 ms | ~59 ms | **635** |
| pylsp | 139 ms | 257 ms | 22 ms | 78 |
| jedi | 461 ms | 264 ms | 22 ms | 78 |

**jedi and pylsp are not faster — they are answering a smaller question.**
Ground truth is 757 word-boundary occurrences across 116 files; basedpyright's
635 is credible once strings and comments drop out, and 78 is roughly a tenth of
reality. A find-references that silently misses 90% of hits is not a speed
option, so **basedpyright is the only one of the three usable**, and the rest of
this file uses it.

**The first call returns a wrong answer, not just a slow one.** On `rich` the
cold call reports **12** references; on `pandas`, **168** against a settled 997.
basedpyright answers before indexing completes rather than waiting. This is
worth more attention than the latency: a user who runs `gr` immediately after
opening a project gets a confidently incomplete list with nothing marking it as
partial.

`pandas`, cursor on `class DataFrame`:

| call | time | refs |
|---|---|---|
| cold | 2806 ms | 168 *(wrong)* |
| 2nd | 1789 ms | 997 |
| 3rd / 4th | ~215 ms | 997 |

## Layer 2 — the picker

Driven in a **real kitty + niri TUI** over Neovim's `--listen` socket, so these
are genuine interactive numbers rather than headless approximations:

- `FzfLua lsp_references`, warm, 997 results: **500 ms** keypress → picker up.
- The server alone for the same query: **215 ms**.
- So the picker costs roughly **285 ms** on a 997-result set.

For reference, on the same live instance: file picker (`FzfLua files`)
**20.5 ms**, grug-far **10.8 ms**. Pickers are not inherently slow — rendering a
thousand LSP results is.

## Layer 3 — the keybind itself, worth ~1000 ms

Neovim ships six built-in `gr*` mappings (`grr`, `grn`, `gra`, `gri`, `grt`,
`grx`). A config that binds bare **`gr`** makes it an **ambiguous prefix**, so
Neovim waits the full `timeoutlen` — default **1000 ms** — before it will even
start. `gr` is also a built-in operator (virtual replace), which this session
proved the hard way by corrupting a test file with stray keystrokes.

**The author has said this is additive, not the cause, and that is right** — but
it is a free second, recovered by binding `grr` or a leader key instead of `gr`.

## Putting it together

Warm, idle, `pandas`-sized project: **~1500 ms** (1000 timeout + 215 server +
285 picker). Cold: **~4100 ms**, and the answer is wrong.

**This does not yet fully explain "extremely slow", and that gap should not be
papered over.** Two candidates, neither confirmed:

1. **Machine load.** `benchmarks/3.4` already documented the Omarchy desktop at
   **load 32.5 on 24 cores** during ML training, inflating identical primitives
   **2.5–2.9x**. Applied to the cold path that is ~10 s — which does match the
   complaint. **This is the leading hypothesis and it is cheap to test:** run the
   same lookup on that machine idle vs. loaded.
2. **A different picker.** These numbers are fzf-lua. A preview-opening picker
   over 997 results does substantially more file I/O.

## A hypothesis that was killed

**An in-project virtualenv makes no difference.** A 41-file project with a 156 MB
venv (2,251 `.py` files) inside it returned references in **2.7 ms warm**, and
renaming `venv/` → `.venv/` changed nothing (2.7 vs 2.6 ms). basedpyright does
not drag the environment into a reference search, whether or not the directory
is dot-prefixed. Recorded because it is the obvious suspect and it is wrong.

## What to do about it

Nothing here is applied; all of it needs the author's sign-off.

1. **Do not bind bare `gr`.** Free second, no downside.
2. **Use basedpyright**, and treat the first result after opening a project as
   untrustworthy — it is not merely slow, it is incomplete.
3. **The picker is worth choosing on this axis**, not on file-search speed where
   everything is already instant.
4. **Test the loaded-machine hypothesis on the desktop before anything else** —
   if it holds, the fix is scheduling ML work, not changing editors.
