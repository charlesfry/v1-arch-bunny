# Phase 3 — Neovim startup: the distro bake-off, and a 34 ms bug under both

`bunne-test`, 2026-08-21, **idle**, no conda on the box, `~/t-nvimbench/sample.py`
= 1502 lines of numpy/pandas-flavoured Python. Both distros installed from their
upstream starters into throwaway `NVIM_APPNAME` dirs (`nvim-lazy`, `nvim-chad`),
so neither touches a real config. `hyperfine`, 20 runs, 3 warmups.

## The headline is not the bake-off

**Opening any `.py` file costs ~34 ms in a Neovim provider probe that fails.**
This is upstream default behaviour and it applies to bare `nvim`, to LazyVim and
to NVChad equally — it is not a distro problem and switching distros does not fix
it.

| Configuration | opening `sample.py` (ms) |
|---|---|
| bare `nvim`, default | 50.9 ± 2.8 |
| bare `nvim`, `g:python3_host_prog` pinned | **16.7 ± 1.0** |
| bare `nvim`, provider disabled | 14.8 ± 0.6 |
| LazyVim, default | 208.8 ± 2.5 |
| LazyVim, pinned | **175.9 ± 2.2** |
| NVChad, default | 20.5 ± 0.7 |

`--startuptime` names the culprit directly: `ftplugin/python.vim` pulls in
`provider/python3.vim`, **36.9 ms of self-time**, the single largest line in the
profile. Pinning the interpreter skips the search and recovers ~34 ms on every
Python file opened, in every configuration tested.

## But the obvious fix is a trap, and it is *the same trap as the Jupyter gripe*

`python-pynvim` is **not installed on this machine**, so:

| | `has('python3')` | what happens when Python is actually used |
|---|---|---|
| default | `0` | `E319: No "python3" provider found. Run ":checkhealth vim.provider"` |
| **pinned** | **`1`** | `E5108: Failed to load python3 host` + a Lua stack traceback |
| disabled | `0` | `E319`, as above |

Pinning alone buys 34 ms and **makes feature detection lie**: `has('python3')`
reports 1 while nothing can run. The clean, greppable `E319` becomes a traceback
that surfaces far from its cause. `CLAUDE.md`'s cautionary example is the
predecessor's silent `image_terminal()` gate — *"the config was not buggy; it was
quiet"* — and this is the same shape of failure in the same workflow.

**So pinning is only correct together with `pynvim`.** `python-pynvim 0.6.0-2` is
in `extra`; molten/Jupyter needs a working provider regardless, so this is a
dependency the DS workflow already implies rather than a new cost. It runs
nothing at idle and adds no boot or resident cost.

**Recommended, for the author to approve** (`CLAUDE.md` requires consultation
before adding a package on low-bar reasoning): install `python-pynvim`, **then**
pin `g:python3_host_prog` to the interpreter that has it. That is a strict
improvement on all three axes — 34 ms faster per `.py` open, the provider
actually works, and `has('python3')` stops lying. **Not applied; needs root and
your sign-off.** Note the pin must point at whichever interpreter carries
`pynvim` — with Miniforge in play (absent here) that is a live question, not a
constant.

## Where NVChad's speed actually comes from — and why it bites the Jupyter gripe

NVChad opens `sample.py` in **20.5 ms**, *faster than bare `nvim`'s 50.9 ms*.
That is not possible by loading plugins, and it isn't: `NvChad/lua/nvchad/options.lua`
lines 48-51 disable **all four** host providers outright.

```lua
g.loaded_node_provider = 0
g.loaded_python3_provider = 0   -- <-- this one
g.loaded_perl_provider = 0
g.loaded_ruby_provider = 0
```

LazyVim leaves them unset (`has('python3')` = 0 in both, but for different
reasons — NVChad by decision, LazyVim because `pynvim` is missing).

**Two consequences, and the second one matters most:**

1. A meaningful slice of NVChad's advantage is **one config line, not
   architecture**. LazyVim can have those ~34 ms for free.
2. **`loaded_python3_provider = 0` disables exactly what molten/Jupyter needs.**
   Picking NVChad as-is would ship a config that silently cannot run the
   author's headline gripe-3 workflow. It would have to be re-enabled, giving
   the 34 ms straight back unless `pynvim` is installed and the host pinned.

So the provider fix is not a tiebreaker between the distros — **it is required
under either of them**, and the distro decision should be made on the ~165 ms
that survives it.

## The distro comparison, with the caveat that makes it honest

| | plugins | loaded on a `.py` file | `sample.py` (ms) |
|---|---|---|---|
| LazyVim | 32 | 13 | 208.8 ± 2.5 |
| NVChad | 27 | **4** | **20.5 ± 0.7** |

**This is a 10x gap and it is not a like-for-like result.** LazyVim loads three
times as many plugins because its starter enables substantially more out of the
box — LSP, completion, treesitter, gitsigns, linting. NVChad's starter is
deliberately close to bare. **Reading this as "NVChad is 10x faster at the same
job" would be exactly the error `CLAUDE.md` warns about** — measuring the easy
axis and letting it stand in for the answer.

What the numbers *do* support:

- The bare-`nvim` floor opening the same file is **14.8 ms**. NVChad's starter
  costs ~6 ms over bare; LazyVim's costs **~194 ms**.
- Roughly **165 ms of LazyVim's cost survives the provider fix**, so the provider
  is not LazyVim's problem — its plugin set is.
- Deciding this properly needs the two configured to the *same* capability set
  (`02-functionality.md`), then re-measured. That work is not done, and no slot
  should close on this table alone.

## Measurement note — the first run of this was wrong

The initial LazyVim figure was **174.7 ms ± 9.6**, taken while `mason` and
`nvim-treesitter` were **still downloading parsers in the background**. Settled,
it is **208.8 ms ± 2.5** — *slower*, because the parsers now exist and load. The
tell was the σ: 9.6 ms against 2.5 ms once quiet. **Discard any Neovim benchmark
taken within a few runs of a plugin install**, the same rule `3.3` established
for initramfs regeneration.

## The other half — RAM

Measured as **PSS** (per `BUDGET.md`'s correction), in a real kitty window on
niri, 12 s after opening `sample.py`, summed across *both* Neovim processes.

| | PSS |
|---|---|
| LazyVim | **35.6 MB** |
| NVChad | **16.7 MB** |
| *kitty alone, for reference* | *175.8 MB* |

LazyVim costs **+18.9 MB** over NVChad — real, but worth the context that **the
terminal it runs inside costs 175.8 MB**, roughly 5x the entire LazyVim session.
On 2b grounds the editor choice is close to noise next to the C5 graphics
requirement already accepted in `3.7`. **The 2a gap (~188 ms per file open) is
the one that should drive this decision, not the RAM.**

### Methodology note: Neovim is two processes

`pgrep -x nvim | head -1` returns the **wrong one**. A TUI Neovim runs a thin
client (~4.4 MB PSS) plus `nvim --embed` doing the actual work (~32.2 MB PSS).
Measuring only the first reports ~4.4 MB for every configuration, which is how
this run first produced an identical, obviously-wrong 4.4 MB for both distros.
Sum every `nvim` pid, or measure the `--embed` one.
