## 1 · MUB package sweep

`pacman -Rns cava fastfetch gpupaper matugen dms-shell` took 54 packages with it —
the whole `hypr*` stack `dms-shell-hyprland` had dragged in, plus `quickshell`, the
`qt6-*` set, `accountsservice`, and `xorg-xwayland`. A second pass removed the last
orphan (`gpupaper-debug`). After:

```
hypr count: 0
orphans:    0
niri:       config is valid, session still running (IPC answered)
```

`xorg-xwayland` going out matches the `xwayland` row (`deferred` — no X11 support at
all right now); `accountsservice` going out removes a daemon nobody chose — and one that
was never rowed or budgeted, having arrived as a *trial's* dependency. That is worth
noticing on its own: a package installed to look at something can leave a daemon behind
that the ledger never sees.

**Correction (DA round, 2026-08-25).** An earlier draft of this section said *"`pacman
-Rs` only takes dependencies nothing else needs, so the removal set is the package
manager's own answer, not an opinion."* **That is wrong, and it was the whole basis for
the no-collateral-damage claim.** `man pacman` on `-s`: removal is skipped only where a
package is *"required by other packages"* or *"explicitly installed by the user"* —
**hard depends only**. Optional dependencies are invisible to it, and several removals
here are optdepends of packages still installed (`libdecor` of `gtk3`; `xorg-xwayland`
of `wlroots`). Nothing was laundered by the tool; the removal set was still a choice.

**So scope this claim down to what was actually tested:** no `hypr*` packages remain and
no orphans remain, both by direct query, and `niri validate` still passes. **Nothing was
launched** — those queries touch no removed library — and *"complete"* was never measured
either, since `-Rs` leaves anything explicitly installed. A `pacman -Qe` diff against the
pre-MUB explicit set is what would settle completeness, and it wants the box.

## 4 · `nvidia-open-dkms` → `nvidia-open`

Same driver version on both sides (610.57.04), so this is a packaging swap and not a
driver change. `nvidia-open` `Conflicts With: nvidia` and, in practice, with
`nvidia-open-dkms` too, so the transaction is a replace. Afterwards `dkms` and
`linux-headers` were orphaned exactly as the row predicted (`pahole` came out with
them) and were removed.

Post-reboot: `NVRM version: … 610.57.04 Release Build (root@)` — the `(root@)` build
stamp is the prebuilt one, against the dkms build's own stamp. **The swap installed
correctly and the prebuilt module loads. That is the whole of what this test shows.**

**Two claims retracted (DA round, 2026-08-25), both control-void:**

- **Idle power.** 8.71 W here against 9.25 W on 08-24 was written up as "within noise".
  The noise was never measured. Both are **single samples**, from different sessions,
  different boots, and different post-boot ages (~4 min vs 45 s), with no interleaving
  and no control for panel or thermal state — and the 5.8 % gap happens to favour the
  change, which is when that framing is least defensible. **No power claim is made here.**
- **Boot time.** There is no before/after at all. `systemd-analyze` prints
  `3.060s (userspace)` and `graphical.target reached after 3.059s` **in one output**; the
  "before" figure quoted in the first draft was that same pair. Worse, the metric cannot
  test the hypothesis: dkms and prebuilt produce the same `.ko`, loaded in the initramfs
  phase, not in userspace. **Struck.**

**And the benefit is one-sided as originally written.** "One fewer thing that can fail
after a kernel update" *moves* a failure mode rather than removing it: the prebuilt
module is path-pinned to one exact kernel (`/usr/lib/modules/7.1.9-arch1-2/extramodules/`),
so a partial upgrade, an LTS kernel, or `linux` landing ahead of its matching
`nvidia-open` leaves no module at all — where dkms would have rebuilt. That interacts
directly with item 2 of this same session: **booting an older snapshot's kernel.** The
dkms rebuild time this trades away was also never measured. The switch still looks right
for a single-kernel machine; the ledger entry should say so rather than claiming a
verified win.

## 3 · Docker subvolumes promoted to the btrfs top level

Instrument: [`instruments/4.24-docker-subvol-promote.sh`](instruments/4.24-docker-subvol-promote.sh).

Before, both subvolumes were nested under `@` (`top level 256`), so a rollback of `@`
would have produced empty directories at those paths — un-capped Docker, gripes #1
and #2 back. After:

```
ID 329 gen … top level 5 path @containerd
ID 330 gen … top level 5 path @dockervol
```

mounted from `/etc/fstab` exactly like `@home`, with the same
`noatime,compress=zstd:1` options. The move copies no bytes: a `btrfs subvolume
snapshot` taken *at the top level* is itself a subvolume, so promoting is one command
per subvolume plus a delete of the nested original.

Caps re-applied (100 GiB `@containerd`, 50 GiB `@dockervol`) and `btrfs quota rescan
-w` run — the mandatory line the row already flagged. The pre-existing "qgroup data
inconsistent" warning cleared with it.

**Cap re-proven, and a canary-design trap found on the way.** First canary wrote
32 MiB of `/dev/zero` against a temporarily-lowered 8 MiB cap and **passed** — because
the filesystem is mounted `compress=zstd:1` and zeros compress to nothing (referenced
after the write: 1.18 MiB). *A byte-cap canary on a compressed filesystem must use
incompressible data or it tests nothing.* Redone with `/dev/urandom`:

```
dd: error writing '/var/lib/docker/.cap-canary': Disk quota exceeded
0/330   7.98MiB   7.98MiB   8.00MiB   @dockervol
```

The cap bites at the byte. Caps restored, canary removed. (The 4.5 instruments
already used `/dev/urandom` — this trap is recorded because the next person writing a
quota check will reach for `/dev/zero` first, as I did.)

Reboot-verified: both subvolumes mounted from fstab on a cold boot, both caps intact,
zero failed units, `docker.socket` active.

**Scope, corrected after a DA round — the summary line "cap re-proven" was doing too
much work:**

- **`@dockervol` only.** `@containerd`'s 100 GiB cap is a *different qgroup on a
  different subvolume at a different mount*, and has no evidence at all on the new
  layout. Untested.
- **At a synthetic 8 MiB, through `dd`, not through docker.** That btrfs returns EDQUOT
  to a writer is proven. That docker survives EDQUOT mid-pull with an intact layer store
  is not, here; 4.5 tested that on the *old* layout, which is a different target, not a
  citation.
- **The unit is compressed on-disk bytes, and nobody said so.** The first canary is the
  proof: 32 MiB of zeros referenced 1.18 MiB. So "50 GiB cap" means 50 GiB *on disk*, and
  the volume of image *content* it permits is unbounded above that. That is the right
  unit for a disk-full gripe — but "a 50 GiB cap on Docker" reads as a cap on images, and
  it is not.
- **The entire point of the change is unexercised.** "A rollback of `@` now leaves these
  subvolumes intact" is why the move was made, and nobody has rolled anything back. By
  this repo's own rule that is **broken until demonstrated**, and the rollback acceptance
  test is what closes it — [`instruments/4.25-rollback-acceptance.sh`](instruments/4.25-rollback-acceptance.sh)
  now does the two halves around the keyboard step. Until it runs, gripes #1 and #2 are
  *not* closed by this row.
- **Every qgroup figure predating tonight's rescan was read while btrfs itself said the
  data was inconsistent** — the standing warning, with the qgroup claiming 1019 MiB
  against `du`'s 400K. Numbers taken under that warning, in this or any earlier
  benchmark, deserve a second look.

**And a defect in the instrument, found by the same round and fixed rather than noted.**
`btrfs subvolume snapshot` does **not** recurse into nested subvolumes, and docker's
btrfs storage driver makes one subvolume per image layer. This box had **zero images**,
which is precisely why the hazard could not surface here — the migration was validated in
the one state where its central failure cannot happen. Run unguarded on a populated
machine, the script produces a `@dockervol` that looks migrated and holds no layers, then
aborts at the delete with fstab unedited. The script now refuses when either source has
nested children.

## 7 · satty keybind + the C4 round trip

Bind added to both the repo config and the box:

```kdl
Mod+Print { spawn-sh "grim -g \"$(slurp)\" - | satty -f -"; }
```

`scripts/check-keybinds.sh`: 121 chords, no duplicates. `niri validate`: valid.

Run live over IPC: satty opened as the only window (`app_id com.gabm.satty`) with a
640×400 image loaded, matching the geometry grim was fed. Screenshot:
`raw/4.24.satty-c4-proof.png`.

**Downgraded after a DA round, and the criticism is exactly right: the test was
constructed so that pass and fail look identical.** The captured region was empty
desktop, so the image satty holds is a **flat RGB(15,15,15) field** — the same colour as
the `swaybg` background around it. A wrong region, a wrong stride, a wrong pixel format,
a scaled or half-drawn frame all render to that same flat field. What the artifact
actually establishes is narrow: **a 640×400 PNG of one uniform colour reached satty, and
it was `0f0f0f` rather than `000000`, so it is not a zeroed buffer.** Aiming grim at a
region containing glyphs would have cost nothing and been decisive. It was not done, and
cannot be until the box returns.

Two further gaps, both real:

- **The command tested is not the command bound.** The bind is
  `grim -g "$(slurp)" - | satty -f -`; what ran was a hardcoded geometry plus
  `--output-filename`. `slurp` — the entire interactive half — was never exercised.
- **`slurp`'s cancel path is the common gesture and is silent.** Press Escape and slurp
  exits non-zero with empty stdout, `grim -g ""` fails, and satty gets an empty stream —
  inside `spawn-sh`, with no terminal, so whatever happens happens invisibly. That is a
  "fail loudly, do not degrade silently" gap on the **default** user action, not an edge
  case, and it wants a decision (a guard in the bind, or an accepted silence).

The clipboard round-trip (`wl-copy --type image/png` → `wl-paste` → `cmp`, identical) is
a clean result **about wl-clipboard**, not about satty; it was placed next to the satty
claim in a way that lent it credit it had not earned.

So C4's remaining acceptance is: one real annotate-and-export by hand, plus a decision on
the cancel path.

### Side finding — the documented lock diagnostic was wrong in the dangerous direction

`benchmarks/4.15` (and the morning report, the resume, and nix-bunne's round-15 log)
recorded `pgrep -f swaylock` as *the* one-liner for "did the session lock silently
eat my IPC spawn". Running it here answered **LOCKED on a freshly booted, unlocked
session** — and the spawn it was supposed to explain then worked fine.

`-f` matches the whole command line, and the shipped idle watcher *is*

```
swayidle -w timeout 900 "swaylock -f -c 0f0f0f" timeout 960 … before-sleep "swaylock -f -c 0f0f0f"
```

so the string `swaylock` is in swayidle's arguments on **every** running session, plus
in the argv of the shell asking the question. The correct one-liner is `pgrep -x
swaylock` (exact process name), verified in both directions here. Corrected in 4.15,
`docs/resume.md`, `docs/morning-report-2026-08-25.md` and `docs/open-questions.md`.

A diagnostic that fails toward "the bug is present" is worse than no diagnostic: it
sends the next reader hunting a lock that is not there.

**Two things the replacement should carry with it, or it is the same failure one layer
down:**

- **`pgrep -x` is a name-exact match**, so it answers "unlocked" for `hyprlock`,
  `gtklock`, or any wrapper not literally named `swaylock`. Correct for BunnE, which
  ships swaylock (`lock-idle`); wrong the moment the locker changes. The one-liner is
  now recorded in four documents across two repos, so the assumption travels with it.
- **This box runs a 28800 s idle timeout instead of the shipped 900 s** (a documented
  test-rig deviation). That is why a one-minute-old session had no locker, and it means
  the run says nothing about the shipped config's locking behaviour. The finding itself
  survives — it is about argv matching, not timing — but "verified in both directions"
  was verified on a session that could not have locked.

## 2 · Snapshot + kernel boot entries — installed, configured, and then I broke the menu

Everything up to the last step worked, and the last step is a config mistake I made
with a known-good reference sitting on the desktop I was typing from.

### What is in place and correct

- `[omarchy]` appended **last** in `/etc/pacman.conf` with `SigLevel = Required
  DatabaseOptional`, exactly as the row specifies.
- Publisher key `40DFB630FF42BCFFB047046CF0134EE680CAC571`
  (`Omarchy <pkgs@omarchy.org>`, ed25519) received from `keys.openpgp.org` and
  `--lsign-key`ed. `pacman-key --list-sigs` shows it at `[ full ]` with the local
  signature from the machine's own Pacman Keyring Master Key.
- `limine-snapper-sync 1.31.0-1` and `limine-mkinitcpio-hook 1.37.1-1` installed from
  it, both signature-validated by that key.
- **The row's zero-resident claim is confirmed on this machine, not just the
  desktop.** With `inotify-tools` absent, the unit logs *"inotifywait is not
  installed. Falling back to Snapper plugin integration."* and exits:
  `MainPID=0`, `MemoryCurrent=[not set]`. Enabled as a boot-time one-shot.
- `limine-mkinitcpio-hook` did the ESP work itself: content-hashed kernel +
  initramfs under `/boot/<machine-id>/linux/`, a `limine_history/` copy per snapshot,
  a `Limine` UEFI entry (`Boot0001`), and a rewritten `limine.conf`.
- `/etc/default/limine` created for BunnE's deviations — upstream explicitly says to
  override there rather than edit the pacman-owned `/etc/limine-entry-tool.conf`.
  One deviation so far: `FIND_BOOTLOADERS=no`, because the auto-discovered "EFI
  fallback" entry pointed at `/boot/EFI/BOOT/BOOTX64.EFI`, which on this machine is
  **byte-identical to `limine_x64.efi`** — an entry that chainloads the menu you are
  already looking at. The stale entry was removed with `limine-remove-entry`.
- `limine-list` then read:

  ```
  Arch Linux
  ├─ linux
  └─ Snapshots
     └─ 77 │ 2026-08-25 17:28:39
  ```

  which is the shape the row asked for.

### The mistake

The hook adopted the pre-existing hand-written `/Arch Linux` entry rather than
creating its own, and left that entry's original `protocol:` / `path:` / `cmdline:` /
`module_path:` lines sitting between the entry title and its new `//linux` child.
`CONFIG.md` says a menu entry becomes a directory only when a sub-entry follows it
with at most a `comment:` in between — so I stripped those four lines to make
`/Arch Linux` a clean directory, added the `comment: machine-id=…` the tool
recommends, re-ran `limine-update` (which preserved the shape), and rebooted to
verify.

The box has not come back, against four earlier reboots the same evening that each
returned in 60–90 s.

### The mechanism, read from limine's source rather than inferred

The first version of this write-up asserted the menu-wait behaviour from `CONFIG.md`.
It is not in `CONFIG.md` — a DA round said so, and it was right, and the remedy did not
need the test box. Limine is open source; `common/menu.c` at the `v12.5.2` tag (the
version in `extra`) settles it outright:

```c
if (max_entries == 0 || selected_menu_entry->sub != NULL)
    skip_timeout = true;                       /* line 1962 */
```

**A directory as the selected entry forces the timeout off.** The countdown never runs;
the menu waits for input indefinitely. It does not eventually fall through to something
bootable. And at the `autoboot:` label (line 2119):

```c
if (selected_menu_entry->sub != NULL) {
    selected_menu_entry->expanded = !selected_menu_entry->expanded;
    goto refresh;
}
```

**Enter on a folder expands it. It never boots.** So the recovery is `Enter` (expand),
`↓`, `Enter` — three keys. The earlier "one keypress" was wrong on the write-up's own
stated facts (the folder is collapsed *and* already selected), and understating a
recovery procedure is worse than not writing one.

Two more things fell out of the same read, both of which change the advice:

- **`print_tree()` counts an entry, then counts its children only if the directory is
  `expanded`.** So a numeric `default_entry` indexes the *visible* tree, and the `+`
  prefix is **load-bearing for the numbering, not decoration**. `default_entry: 2`
  *without* `/+Arch Linux` puts the index out of range — a half-applied repair is not a
  partial improvement, it is a different failure.
- **`find_entry_by_path()` — the non-numeric `default_entry` form — expands every
  directory along the path and matches only where `sub == NULL`.** A path-form default
  is therefore *structurally incapable* of selecting a folder, and immune to
  `limine-entry-tool` renumbering entries (which this session watched it do, when
  `FIND_BOOTLOADERS` inserted one). **`default_entry: Arch Linux/linux` is the repair**,
  not `default_entry: 2` — one line with no second half to forget.

`CONFIG.md` cannot settle any of this; it is internally inconsistent on the point
(*"the timeout in seconds before the **first** entry is automatically booted… If set to
`0`, boots **default** entry instantly"*), and it describes the path form in a clause
this write-up originally truncated away. **The lesson is narrower and sharper than
"read the reference": the reference was the wrong document.** For behaviour, the source
is the reference.

### RESOLVED 18:30 — the hypothesis was right, and the journal proves it

The box came back at 18:27:30 (a human at the keyboard; `limine.conf` was byte-unchanged
at my 17:31 mtime, so nothing had been repaired). That made the decisive evidence
available, and it is better than the reasoning it replaces:

```
$ sudo journalctl --list-boots | tail -3
 -2 …  Tue 2026-08-25 17:15:11 EDT   Tue 2026-08-25 17:23:38 EDT
 -1 …  Tue 2026-08-25 17:24:37 EDT   Tue 2026-08-25 17:31:49 EDT
  0 …  Tue 2026-08-25 18:27:30 EDT   …
```

**A 56-minute hole with no kernel start in it.** The journal's clock begins when the
kernel does, so a machine sitting at a LUKS prompt from 17:34 would have opened boot 0 at
~17:34, not 18:27:30. It did not. The machine was **pre-kernel** for the entire window,
which is the bootloader — and it eliminates hypotheses 2 and 3 outright: a LUKS prompt
means the kernel is already running, and a hash-mismatch panic loops rather than sits.
Hypothesis 1, the menu wait, is the only one left standing, and it matches the mechanism
read from the source.

**The check was also finally run against the real file**, which the DA round had
correctly flagged as never having happened — it FAILs it, naming the directory and the
repair. That closes the "it has only ever seen a reconstruction" caveat for check 1.

### The repair, applied and reboot-verified

`default_entry: 2` plus `/+Arch Linux`. **Not the path form**, despite this file
recommending it — and the reason is worth stating, because it is the same judgement that
was missing this afternoon. The index-plus-expanded shape is what the author's own
working desktop config runs on this exact limine version; the path form is better on
paper and has never been observed to boot anything. A machine whose recovery had just
been performed by hand is the wrong place to debut an untested spelling. **The path form
remains the right installer default — after someone has watched it boot once.**

`limine-update` was re-run immediately afterwards and **preserved both lines**, which was
the specific worry about hand-editing a tool-managed file. `scripts/check-limine.sh` goes
FAIL → `ok: … default_entry 2 resolves to a bootable entry; 4 boot() file(s) present`.

Then the measurement that settles it — same machine, same everything, two config lines
apart:

| config | shutdown → next kernel start | ended by |
|---|---|---|
| broken | 17:31:49 → 18:27:30 — **56 min** | a human at the keyboard |
| repaired | 18:29:38 → 18:29:54 — **16 s** | nothing; unattended |

Zero failed units, booted `rootflags=subvol=@`. That is a genuine before/after with one
variable, which is more than most of this session's other claims managed.

### What was still a hypothesis, before that

Kept for the record, since the ranking was made before the answer was available. The
mechanism was proven from source; **that the box was sitting in it was not** — nobody had
seen the screen, and the machine was unreachable.

Argument for: `BootNext=0001` is one-shot and `BootOrder` was restored NixOS-first, so
had the firmware failed to launch limine at all, the *next* boot lands in NixOS, which
answers on the network. It does not. So something launched and stopped, rather than
nothing launching. A LAN sweep of the subnet also found no laptop on any other address,
so it is not simply a changed IP.

Ranked alternatives, none excluded:

1. **The menu wait** — mechanism proven, matches every symptom.
2. **A LUKS passphrase prompt.** The box normally auto-unlocks from a keyfile in the
   initramfs (`benchmark-unlock`), and the initramfs was rebuilt twice that evening —
   once by `nvidia-open` (after which it booted fine) and once by `limine-update`, whose
   output the machine had never booted before it stopped answering.
3. **A limine hash-mismatch panic.** `limine-entry-tool` ships `ENABLE_VERIFICATION=yes`
   and puts a `#<blake2>` on every path; **`hash_mismatch_panic` defaults to
   panic** (`CONFIG.md` line 118). `bunne-test` does not set it. The author's desktop
   config *does* — `hash_mismatch_panic: no` — which is the second time the known-good
   reference contained the answer to a question this session did not think to ask of it.
   A panic is not fixed by any keypress; it needs the config repair from a live system.
4. Powered off, or a hardware fault coincident with the reboot.

**Telling them apart takes one glance at the screen**, which is why the recovery note
covers all three.

### The recovery procedure, kept because it will be needed again

Done, but this is the class of failure that recurs, so the steps stay written down.

**At the menu:** `Enter` (expands `Arch Linux`) → `↓` (to `linux`) → `Enter` (boots) —
three keys, because `Enter` on a folder only expands it. If it is a LUKS prompt instead,
type the passphrase. If it is a hash-mismatch panic, neither helps: boot NixOS (plain
reboot; `BootOrder` is NixOS-first) and repair the Arch ESP from there.

**Then fix the config**, and *always re-run `limine-update` and then
`scripts/check-limine.sh`* — in that order, because `limine-update` rewrites the file and
the check is what proves it did not undo the repair. It preserved both lines here, but
that is an observation, not a guarantee.

ESP backups from this session: `/boot/limine.conf.pre-restructure.bak` (the shape that
booted before the restructure), `/boot/limine.conf.pre-repair.bak` (the broken shape, kept
as a test fixture) and `/boot/limine.conf.old` (the tool's own rolling backup).

**Still open, and it belongs to the same sitting as the acceptance test:** `timeout: 1`
leaves a one-second window to reach the snapshot menu. Fine for every ordinary boot, poor
for the one moment the menu exists to serve. The desktop ships `timeout: 60`.

### Why this was not a bricking risk, and where the mitigations fell short

The mitigations in place: NixOS on a **separate ESP** (`p1`, its own `Boot0007`), so a
broken Arch bootloader config cannot take the machine off the map; snapper snapshots
either side of every package transaction; two copies of the previous `limine.conf`. All
of that survives, and is why the fix is keys-and-a-line rather than a USB stick.

What none of it covers is the failure that actually happened: **a bootloader that is
neither booting nor failing, just waiting.** `panic=30` reboots a kernel that panics;
nothing reboots a menu. For an unattended change to a boot path, "it will fall through
to the other OS if it goes wrong" is only true if the wrong thing *terminates*.

### What came out of it: `scripts/check-limine.sh`

Written the same evening, because limine ships **no validator** and the failure mode was
a file that parsed perfectly. Two checks that carry an exit code:

1. **The default entry resolves, and resolves to something bootable.** FAIL if a numeric
   `default_entry` (explicit or the implicit `1`) lands on a directory *or* out of range
   — the out-of-range case being the collapsed-directory trap, which is a real failure
   and not the style warning the first draft made it. FAIL if a path-form default names
   nothing. The message carries the path-form repair, derived from the file.
2. **Every `boot():` file an entry boots from exists on the ESP.** FAIL otherwise — the
   black-screen case `rollback-method` warns about, made mechanical.

**The pass line says what was checked, not "all good".** That is a correction, not a
flourish: the first draft printed *"default_entry N is bootable, all booted files
present"* on two configurations it had never inspected — a non-numeric `default_entry`
(check 1 skipped wholesale, assurance printed anyway) and any `path:` not using
`boot():`, of which the author's own desktop config has one. A check that hands out
false assurance is worse than no check, and it was the project's own "degrade silently"
prohibition being broken by the script written to enforce it. It now reports e.g.
`3 boot() file(s) present; 1 path(s) NOT checked — not boot()-relative`.

`--self-test` builds the failing config and **three near-misses** — the index repair
applied without the `+`, a path-form default naming nothing, and a missing boot file —
and asserts each is rejected while both correct repairs pass. Green against the author's
working Omarchy `limine.conf`. **Two limits worth stating:** the self-test rejects a
*reconstruction* of the 2026-08-25 config, not the file itself (which is on an
unreachable ESP), and the one real config it has been run against is the same one the
indexing model was checked against — one machine, not an independent sample. The model
itself is read from source, not inferred, which is what makes that acceptable rather
than circular.

### The process lesson, stated plainly

The change was reasoned from `CONFIG.md` and not checked against either of the two
things that would have caught it, **both available without the test box**:

1. **The working example one `cat` away**, on the machine I was already logged into.
   `CLAUDE.md` says verify on the machine rather than from memory; the same rule points
   at the *known-good instance* of the file being edited, not only at its spec. Reading
   two lines of it and stopping is how `hash_mismatch_panic: no` — sitting in that same
   file, naming a competing failure mode — went unnoticed twice.
2. **The source.** `CONFIG.md` does not describe what a directory-as-default does, and
   is internally inconsistent on the neighbouring sentence. Limine is open source and
   the answer was one function. Asserting a parser behaviour from prose documentation
   *is* asserting from memory, in the sense the rule means.

The sharpest version: **a boot-path edit whose only verification is a reboot has no
verification at all** — the reboot is the experiment, not the check. The check had to
come first, and every input it needed was on the desktop.

A DA round is what forced both readings. It is worth recording that the round was run
*after* the write-up was committed, and that it rejected or narrowed six of seven
conclusions. Running it earlier would not have saved the box — the edit was already
made — but it would have saved a wrong recovery procedure and a check script that
handed out false assurance from being the record for several hours.
