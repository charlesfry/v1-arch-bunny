# 4.6 — terminal input round-trip: 3.7 re-verified, and kitty's 3 ms found

`arch-bunny`, 2026-08-24 ~01:00. Instrument: `instruments/inputrt.py` — runs
INSIDE the terminal under test (invoked directly over SSH against the live
Wayland session; `niri msg action spawn` mangles `-e` argument lists — a
side-finding), puts the tty in raw mode, writes `ESC[6n` (DSR), times to the
terminal's reply. n=50 per cell, warmup drained, loads recorded. Raw:
`raw/4.6.inputrt.jsonl`. This is the terminal's input/parse/reply loop —
3.7's "input-rt" column — NOT keystroke-to-photon.

## Findings

1. **3.7's input-rt ordering and magnitudes replicate** on a new install,
   new kernel, new instrument: sub-ms for foot/ghostty/alacritty, ~3-4 ms
   for kitty. The old column was honest.
2. **kitty's ~3 ms is a config default, not a capability**: `input_delay`
   (default 3 ms, deliberate input coalescing) accounts for nearly all of
   it — the delay knob tracks the measurement almost 1:1 (3→3.6, 1→1.6,
   0→0.53). **`input_delay 0` puts kitty in the sub-ms club.** This sits
   on the exact 2a headline path (keystroke → glyph). The trade, stated
   out loud per the rules: the delay exists to batch input and reduce
   wakeups — `0` means more CPU wakeups under sustained input, a real but
   unmeasured battery/CPU cost. **Candidate config line for `kitty.conf`,
   author's call** — it would be the 4th line of a 3-line config.
3. **zen vs mainline: null on input-rt too** (kitty 3.29 vs 3.28-3.63,
   foot 0.318 vs 0.332, delay0 0.52 vs 0.53 — all within run variance).
   Combined with 4.4's spawn probe, zen now has data on both metrics the
   kernel row queued, and neither moves. The mainline pick stands on
   measurement, not just boredom-preference.
4. Not DA-gated as its own round (informational, changes no row by
   itself); the `input_delay` candidate goes to the author via the
   morning-report queue, and whatever row it lands in cites this file.

Caveat: DSR-reply timing exercises the input→parse→pty-write loop;
keystroke-to-photon adds compositor/present and needs the camera step
(04-plan Phase 1 step 4) — `input_delay` sits inside the photon path too,
so the win is real, but its end-to-end share is unmeasured.
