# Phase 3 — spawn-to-on-screen latency, measured through niri's IPC

`bunne-test`, 2026-08-21, **idle (load 0.00–0.07)**, live niri session, no
desktop apps running. Run by `~/t-winlat.sh`, `~/t-fuzzellat.sh` and
`~/t-bravelat.sh` (scratch scripts, `shellcheck`/`shfmt` clean).

This closes part of the gap `resume.md` named: *"there is no latency baseline for
anything."* It is **not** the whole gap — see the caveat below, which matters
more than the table.

| Path | median (ms) | n | spread |
|---|---|---|---|
| **fuzzel** spawn → surface mapped | **29** | 10 | 24–29 |
| **kitty** spawn → window mapped | **150** | 12 | 146–152 |
| **brave** cold → window mapped | **642** | 5 | 634–711 |
| `bash -lic exit` (login shell) | 74.1 ± 0.6 | 30 | 73.1–75.4 |
| `nvim --headless +q` (no config) | ~11 | 15 | 10.5–13.1 |
| `niri msg version` (IPC floor) | 4.0 ± 0.8 | 20 | 3.7–7.4 |

**Method.** `niri msg event-stream` is timestamped line-by-line in a Python
filter (a per-line `date(1)` fork costs more than the thing being measured),
then a spawn action is issued and the first `Window opened or changed` event
carrying the right `app_id` is matched against the pre-spawn timestamp. This
measures the compositor actually mapping the surface, not a process returning.

**Corrections to apply.** Every row above includes ~4.0 ms of `niri msg` CLI
startup that a real keybind does not pay — niri handles a bound key in-process.
So kitty is **~146 ms** and fuzzel **~25 ms** as a user would experience them.
fuzzel carries one further correction: layer-shell surfaces are *not* reported
by the event stream, so it is measured by polling `niri msg layers`, giving a
resolution of one poll and a result that reads high by up to ~4 ms.

## The caveat that matters most

**This is not keystroke-to-photon and must not be quoted as if it were.** It
starts at a spawn action, not at a key press, and ends when niri says it mapped
the surface, not when a photon leaves the panel. It excludes input-stack latency,
compositor render, and presentation to the display. `04-plan.md` Phase 1 step 4
still stands: the honest headline number needs the phone slow-motion capture, and
this table does not replace it.

What it *is* good for is comparison — these three paths were measured
identically, so the ranking between them is trustworthy even though the absolute
figures are floors.

## How this sits against the terminal bake-off

`3.7` measured kitty's cold start at **177.6 ms** to a shell *running inside* the
window. This measures **~146 ms** to the window being *mapped*. The two are
consistent and complementary: the window appears, then the shell inside it
becomes usable ~30 ms later. Neither supersedes the other, and 3.7's conclusion
is untouched.

## Two findings that were not the point of the run

1. **XWayland is not installed** (`xorg-xwayland` absent, no `Xwayland` binary)
   and Brave runs natively on Wayland regardless. That is a live data point for
   the `xwayland` `deferred` row: nothing tested so far has needed it.
2. **Brave's 642 ms is a throwaway-profile number and is not what the author
   experiences.** Launched against the real profile on this machine, Brave took
   **over 6 seconds** to map a window, because it restored a previous session
   (a YouTube tab). The cold-launch figure is the right one for comparing
   browsers; it is the wrong one for describing the machine. If browser start
   feels slow, session restore is the thing to look at, not Brave itself.
