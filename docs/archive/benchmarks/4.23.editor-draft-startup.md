# 4.23 — p4 nvim draft startup cost (answers morning-report question #10)

Question #10 asked whether to re-affirm or trim the Phase-4 nvim draft, framed as
"~160 ms vs the 126.8 ms the LazyVim decision was made on (+33 ms), candidates
markdownlint / markdown-preview." Measured on `bunne-test`, `2026-08-25`, all
same box / method / day (hyperfine, `--headless +qa <file>`, warm).

## The +33 ms was a cross-method artifact

| open a `.py` | mean |
|---|---|
| baseline LazyVim (`nvim-lazy`) | **145.0 ms** |
| p4 draft (`nvim-p4`) | **159.8 ms** |

Apples-to-apples the python-open delta is **+14.8 ms**, not +33. The 126.8 ms was
4.15's phase-1 number from a different session/method; comparing it to a
freshly-measured 160 ms double-counted the method difference. The draft's own
plugin specs are exactly the gripe-#3 fix — `molten-nvim`, `3rd/image.nvim`,
`venv-selector.nvim` — so this +14.8 ms *is* the notebook capability, not bloat.
No `markdownlint` in the tree at all; `lazyvim.json` has **zero extras enabled**.

## markdown-preview is already free; don't trim it for latency

`markdown-preview.nvim` and `render-markdown.nvim` are installed (pulled by the
notebook stack, not an extra). Startup attribution on a `.md` open
(`--startuptime`):

- **`markdown-preview.nvim` is NOT sourced at startup** — it is command-lazy
  (`:MarkdownPreview`). Trimming it saves **zero** latency; keep-or-cut is a
  feature call (browser preview is arguably redundant with in-editor
  render-markdown + image.nvim), not a speed one.
- `render-markdown.nvim/plugin/…lua` self-cost **0.3 ms**.
- The largest single markdown-open item is nvim's **own runtime**
  `ftplugin/markdown.lua` at **12.8 ms** — present in *both* configs, not the
  draft's fault.

## The markdown path — the notebook path — is nearly free (GUI, after unlock)

The headless `.md` number (p4 215 ms vs baseline 132 ms, +83 ms, σ 26) was an
**artifact**: headless nvim does not fully initialise `image.nvim`, and the run
was noisy. Re-measured in a **real kitty terminal** (`nvim --startuptime`, n=3):

| `.md` open | runs | mean |
|---|---|---|
| baseline LazyVim | 126.5 / 119.7 / 122.3 | **~122.8 ms** |
| p4 draft | 125.6 / 124.1 / 124.4 | **~124.7 ms** |

**+1.9 ms** — the render-markdown path costs almost nothing at startup (image.nvim's
image rendering is async/post-startup, so it doesn't load the open). The heavier
delta is the *python* path (+14.8 ms: molten + venv-selector), not markdown. Both
deltas are small and both are the gripe-#3 capability.

## Answer to #10

**Re-affirm the draft.** The measured cost of the extras over baseline LazyVim is
**+14.8 ms on `.py` open**, all of it the molten/image/venv capability the editor
was chosen to deliver — nothing frivolous to trim. `markdown-preview.nvim` is the
one arguable removal, but on **feature-redundancy grounds, not latency** (it is
command-lazy and costs nothing at startup). GUI markdown-path number now taken
(+1.9 ms) — file closed.
