# 4.29 — what btrfs qgroup accounting costs, and why we are keeping it anyway

**2026-08-26. `bunne-test`, kernel 7.1.9-arch1-2.** Open question 28, raised by answering
26: the Docker qgroup *limits* are gone but `btrfs quota` is still **enabled**, and the
stated reason was that `disk-alert`'s meter 2 reads it for per-subvolume byte figures.
Accounting is not free, so the question was whether one number in a notification that
fires six times a day is worth a per-commit tax.

Instrument: `benchmarks/instruments/4.29-qgroup-accounting-cost.sh`. Raw data:
`benchmarks/raw/4.29.qgroup-cost.tsv`.

## The headline

**The cost is real, it is concentrated almost entirely in one operation, and that
operation is `btrfs subvolume delete` — 46× slower with quotas enabled.** But the question
dissolves rather than resolving, because the premise was wrong: the qgroup is **not** paid
for a notification. `snapper`'s `SPACE_LIMIT` cleanup runs on it.

## Method

A loopback btrfs, fresh per run, mounted `noatime,compress=zstd:1` like the real one. Each
run builds `bunne-test`'s actual shape — a populated subvolume plus **24 snapshots** of it,
because qgroup accounting walks the sharing relationships between snapshots and a test with
one snapshot would measure nothing — then times four metadata-heavy operations. Arms
**alternate** rather than blocking, so machine drift lands on both equally.

The workload is a real `pacman` package (`linux-7.1.9.arch1-2`, 6457 files after
extraction), because untarring thousands of small files is what this machine actually does
to its filesystem. The instrument **refuses to run** if the extract produces fewer than
1000 files — the `docker-storage-quota` canary lesson, where a test that silently did
nothing passed.

n=9 per arm.

## Results

| operation | quota off | quota on | Δ | factor | ranges overlap? |
|---|---|---|---|---|---|
| extract 6457 files | 0.591 s | 0.600 s | +0.009 | 1.0× | **YES** |
| `rm -rf` them again | 0.236 s | 0.271 s | +0.035 | 1.15× | no |
| `subvolume snapshot` | 0.031 s | 0.053 s | +0.022 | 1.7× | no |
| **`subvolume delete` ×5** | **0.038 s** | **1.775 s** | **+1.737** | **46.7×** | no |

Full ranges:

```
extract    off [0.575-0.602]  on [0.589-0.639]
delete     off [0.226-0.245]  on [0.266-0.282]
snapshot   off [0.029-0.034]  on [0.052-0.055]
subvoldel  off [0.034-0.048]  on [1.769-1.817]
```

**The extract row is not a result.** The arms' ranges overlap and the median difference is
smaller than either arm's spread. Writing files is not measurably affected; say that rather
than quoting +1.5%.

**The other three are clean** — no overlap at all, and `subvoldel`'s two clusters are
separated by a factor of forty with within-arm spreads of 0.014 s. That is 0.355 s per
snapshot deleted against 0.008 s, on a **200 MB** subvolume. `bunne-test`'s real root is
~4 GB; this figure is a floor, not a ceiling.

## The instrument trap: `btrfs subvolume sync` measures itself

The first version of the deletion arm reported **28-30 s in both arms**, differing by a
suspiciously exact 2 s. It was `btrfs subvolume delete` followed by `btrfs subvolume sync`,
which reads as the obvious way to wait for the cleaner thread.

Probed directly: the `delete` call returns in **0.02 s**, the subvolumes leave `subvolume
list` after **0.04 s**, and `btrfs subvolume sync` then blocks a flat **~29 s regardless**.
Forcing a commit with `sync` first did not change it. So that arm was measuring
`subvolume sync`'s own polling behaviour, at a magnitude that would have swamped and hidden
the real 1.7 s effect entirely.

`btrfs subvolume delete -C` is the honest instrument: `-C` waits for the transaction commit
that processes the dead roots, which is exactly where the qgroup work happens. **A number
that is identical across both arms of a controlled test is evidence the instrument is
wrong, not evidence the effect is absent.**

## Which bucket does this land in, and who waits for it

`BUDGET.md`'s buckets are per prompt / per terminal / per login / per boot / resident RAM,
and none of them fits. This is a **per-snapshot-deletion** cost, and what deletes snapshots
here is `snapper` enforcing `NUMBER_LIMIT=2-15` on cleanup — a timer, not a keystroke.

So no human sits watching it. **But btrfs transaction commits are filesystem-wide**, which
is the same scoping fact that made `4.27` dangerous: a 1.8 s commit spent on qgroup
accounting is 1.8 s during which other writers to that filesystem wait. A cleanup that
retires several snapshots while the author is saving a file is a stall he can feel. That is
a priority-2a event in a bucket nobody had been counting, which is precisely what
`BUDGET.md` exists to catch.

Not measured, and worth naming: whether that stall is observable end-to-end from a writer's
point of view, and how the 1.775 s scales from a 200 MB subvolume to a 4 GB one.

## And then the premise turned out to be wrong

Question 28 assumed the qgroups now buy exactly one thing: `disk-alert`'s meter 2. They do
not. From `man 5 snapper-configs` **on the machine**:

> `QGROUP=qgroup` — The btrfs quota group used for **space aware cleanup algorithms**.
> Only supported for btrfs.

`/etc/snapper/configs/root` carries `QGROUP="1/0"`, `SPACE_LIMIT="0.08"` and
`FREE_LIMIT="0.2"`. Both limits are space-aware algorithms, so **both run on the qgroup**.
Disabling quotas would not merely cost the alert a number — it would silently switch off
snapper's space-based retention, which is part of gripe #2's fix (`snapshot-bloat`,
`snapshot-system`). Option 3 of question 28 ("disable quotas, get the number from `du`")
is therefore not the cheap swap it looked like: `du` can replace the *meter*, and nothing
in userspace can replace what snapper reads.

**Recommendation: keep the quotas (option 1), with the cost now recorded rather than
silent.** That is what `CLAUDE.md` asks for — a trade stated out loud, in the currency of
priority 2 — and the honest version is: *snapshot deletion costs ~0.35 s per snapshot
instead of ~0.008 s, paid on snapper's cleanup timer, and it buys space-aware retention
plus the alert's numbers.*

## One defect this found, in the thing it was investigating

Following the dependency into `snapper-configs` exposed the same bug in **meter 3** that
answering question 26 had just exposed in meter 2: if `btrfs qgroup show` returns nothing,
`excl` is empty, the meter `continue`s, and the alert reports a healthy machine. Quotas off
would have meant *snapper's retention silently not running* **and** *the alert silently not
saying so* — the exact compound failure `CLAUDE.md`'s fail-loudly rule is written against.

Fixed: an absent snapper figure is now a breach naming the cause. Tested by suppressing the
helper's `snapper` line — `❓ snapper qgroup reports nothing — SPACE_LIMIT cleanup is
UNMONITORED and probably not running`.

**Both of these were reachable by reading and were found by running.** That is two for two
today, and it is worth carrying: the meters are the part of this repo whose failure mode is
silence, so they are the part that most needs exercising rather than reviewing.
