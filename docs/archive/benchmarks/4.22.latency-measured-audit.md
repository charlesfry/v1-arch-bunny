# 4.22 — Latency / Measured-column audit (the priority-2a blind spot)

CLAUDE.md's standing warning: *"If a slot sits in the interactive path, a
`Measured` column with no time in it is an incomplete argument — say so rather
than letting the RAM figure stand in for the answer."* This audit acts on it —
scans every `picked` row, flags the ones a hand actually waits on, and checks
whether each carries a **timing** number or only RAM / nothing.

## Method

`scratchpad/measured_audit.py` parses the tables, buckets each interactive-path
row's `Measured` cell as HAS-TIME / EMPTY / RAM-or-PWR-ONLY, and the judgement
below reviews each flag by hand (the keyword heuristic over-flags).

## Result — the fear was systemic, the reality is one hole

Audited row by row, the interactive-path picked rows are **mostly well-timed
already**: `launcher` 21.9 ms spawn→onscreen, `font` 231/194 ms ligature flood,
`compositor` the multi-GPU hard case, `benchmark-unlock` 17.406 s honest boot,
`python-pynvim` 52.4→12.0 ms per `.py` open, `editor` startup, `gpu-driver` idle
9 W @ P8. Six rows flagged; four are heuristic false positives and one is
low-priority:

- `installer-prompts` (L52) — one-time install UX, not a runtime path. Correctly empty.
- `wallpaper` (L92) — swaybg drawn once at session start; 8.2 MB resident *is* the
  right metric (priority 3 resident cost, not a keystroke path).
- `lock-idle` (L77) — swaylock-vs-hyprlock was decided on resident/dep cost
  (123 KiB, 0 new deps); lock-appear latency isn't the pick axis or a daily hot path.
- `kernel` (L88) — zen is removed, so no live comparison; boot cost is captured in
  aggregate by `benchmark-unlock`. A doc cross-ref at most.
- **`shell` (L44) — the one genuine gap.** Its rationale claims bash *"starts
  faster than fish/zsh"* with no number, and it is the per-terminal path.

## Filling the `shell` gap — and a per-terminal tax that turned out not to exist

Measured on `bunne-test` (hyperfine, `-N`, box's 10-line `.bashrc` / 9-line
`.bash_profile`):

| invocation | mean | what it sources |
|---|---|---|
| `bash --norc -i` | **0.97 ms** | interpreter floor |
| `bash -i` (interactive) | **4.8 ms** | `~/.bashrc` |
| **what kitty actually runs** (`ENV=kitty.bash bash --posix -i`) | **~11.1 ms** (σ 6.4) | kitty shell-integration (414-line `kitty.bash`) + `~/.bashrc` |
| `bash -lic` (login) | **77.0 ms** (65 ms user CPU) | `/etc/profile` + `~/.bash_profile` |

The 72 ms login delta is almost entirely `/etc/profile`, timed alone at
**75.7 ms**. Root cause, read on the box: `/etc/profile.d/vapoursynth.sh` is one
line — `export VSSCRIPT_PATH=$(vapoursynth get-vsscript)` — a command
substitution that forks the vapoursynth binary (→ Python) on every login shell.
This is the same 66–83 ms already in `BUDGET.md` under the vapoursynth entry.

**The question that matters for 2a: does every kitty terminal pay the 75 ms, or
only the once-per-boot login?** Verified from kitty's shipped source, not memory
(`/usr/lib/kitty/kitty/child.py:453–465`): the login-shell `-`-prefix on argv[0]
is gated on `should_run_via_run_shell_kitten = is_macos and is_default_shell`
(`child.py:365`) — **macOS only**. kitty's own comment: *"xterm, urxvt, konsole
and gnome-terminal do not do it… arguable whether graphical terminals should
start shells in login mode."* So on Linux **kitty spawns an interactive,
non-login bash**: it sources `~/.bashrc` (4.8 ms) and never `/etc/profile`.

**Conclusion: the vapoursynth tax is a login-bucket cost (once per boot, on the
tty1 autologin), not a per-terminal 2a cost.** No hidden per-terminal regression
from the login path. This confirms and sharpens the existing BUDGET.md vapoursynth
entry rather than overturning it.

*Empirical confirmation (after unlock):* spawned a real kitty and read its child
via `/proc`. kitty's sole shell child is **`/bin/bash --posix`** (no leading dash
→ **non-login, confirmed** — the source read holds; the two siblings are
`kitten __atexit__` and `kitten __watch_conf__`). The `--posix` is kitty's
shell-integration mechanism: it launches bash in POSIX mode with `ENV` pointed at
`/usr/lib/kitty/shell-integration/bash/kitty.bash`, which re-enables normal bash
and sources `~/.bashrc`.

**New per-terminal finding (uncounted until now).** Because kitty runs its
414-line integration script on every terminal, the real per-terminal shell cost
is **~11.1 ms, not 4.8 ms** — kitty's integration adds **~6 ms** over plain
`bash -i`. Per-terminal is a 2a hot path, so this belongs in BUDGET.md's
per-terminal bucket and is a **features-vs-latency dial for the author**:
`shell_integration enabled` (default; ~11 ms, gives prompt-jump / cursor-shape /
title / clone-in-cwd) vs `shell_integration disabled` (~4.8 ms, loses them) — or
a partial mode (`no-cursor`, etc.). Stated out loud per the "state the trade"
rule; n small and σ high (6.4 ms), so treat ~11 ms as order-of-magnitude, not
a settled figure. *(Earlier draft of this file said the empirical check was
blocked by an idle-lock — it was, until the author unlocked; that idle-lock was
itself an organic reproduction of the closed spawn-wedge finding, with the benign
two-`swaylock -f` pair confirmed.)*
