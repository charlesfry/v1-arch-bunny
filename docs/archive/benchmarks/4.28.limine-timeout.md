# 4.28 — is `timeout: 3` real, and what does it cost?

**2026-08-26, `bunne-test`.** DA round 19 rejected the claim that open question 22's
`timeout: 3` was "reboot-verified": the box booted through the setting, which proves the
file parses, not that the timeout does anything. **Nobody had timed it.** This times it.

## Result: the timeout is real and costs exactly what it says

| config | shutdown → next kernel start | median |
|---|---|---|
| `timeout: 1` | 15 s, 16 s, 16 s | **16 s** |
| `timeout: 3` | 18 s, 18 s, 17 s | **18 s** |

**Δ = 2 s, which is exactly the 2-second difference between the two settings.** The arms
do not overlap ({15,16,16} vs {17,18,18}). n=3 per arm, interleaved (3,3,1,1,1,3) so drift
across the session cannot produce the gap.

So open question 22's decision is now costed rather than assumed: **the recovery window is
genuinely three seconds, and it is paid on every single boot** — the priority-2a charge the
author accepted when choosing 3 over 1.

## Method, and why not `systemd-analyze`

Measured as the gap between the **last journal message of the previous boot and the first
of the next** — the same instrument that diagnosed the 56-minute menu hang in `4.24`. It
is the only window that necessarily contains the menu wait.

**`systemd-analyze` cannot see this, and that is a trap worth recording.** Its `loader`
figure read **3.355 s at `timeout: 1`** and **3.359 s at `timeout: 3`** — a 4 ms difference
across a change that really costs 2 s. Limine populates the systemd-boot loader-interface
EFI variables, so `systemd-analyze` prints a `loader` number and it looks authoritative;
it simply does not include the menu wait. **Anyone budgeting bootloader cost from
`systemd-analyze` would conclude the menu timeout is free.** Given `BUDGET.md` keeps a
per-boot bucket, that is exactly the kind of confidently-wrong number the ledger exists to
prevent.

## Scope

- One machine, one kernel (`7.1.9-arch1-2`), one firmware. The *absolute* 16/18 s figures
  are this laptop's; the **2 s delta** is the transferable result and it matches theory.
- Whole-second resolution — the journal timestamps were truncated to seconds. A 2 s delta
  is comfortably above that, but this method cannot resolve sub-second timeouts, so it
  could not check limine's documented decimal values (e.g. `0.25`).
- **This does not verify `hash_mismatch_panic: no`**, which remains wholly unexercised —
  it acts only on a hash mismatch and there has never been one on this machine. That test
  needs a deliberately corrupted `boot():` file and a human present, because a wrong
  outcome is a machine that hangs pre-kernel and there is no remote power control.
