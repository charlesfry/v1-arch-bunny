# Phase 3 — boot timing with the benchmark keyfile

Measured 2026-08-21 on `bunne-test`, six consecutive boots, same machine and
config throughout. The only variable is whether `CHOICES.md` `benchmark-unlock`'s
keyfile was in place, i.e. whether a human typed a LUKS passphrase.

`graphical.target` is given **in userspace**, derived as the journal's monotonic
timestamp for `Reached target Graphical Interface` minus that boot's `kernel`
phase, so it is directly comparable to `systemd-analyze`'s own wording.

| Boot | Unlock | firmware | loader | kernel | userspace | `graphical.target` |
|---|---|---|---|---|---|---|
| -5 | keyfile (1st boot after `add`) | 4.820s | 1.300s | 6.477s | 4.807s | **4.432s** |
| -4 | passphrase, ~3 min at prompt | 4.837s | 1.301s | 3min 22.176s | 2.195s | 2.194s |
| -3 | passphrase, typed fast | 4.866s | 1.300s | **5.200s** | 2.214s | 2.210s |
| -2 | keyfile (1st boot after `add`) | 4.832s | 1.300s | 6.333s | 3.224s | **3.222s** |
| -1 | keyfile | 4.875s | 1.298s | 6.444s | 2.437s | **2.221s** |
| 0 | keyfile | 4.834s | 1.300s | 6.477s | 2.446s | **2.209s** |

## What is settled

**1. The `kernel` phase was human typing speed, and the keyfile fixes it.**
3min 22.176s left sitting versus 5.200s typed promptly, identical configs. Total
boot time was never a metric; with the keyfile it is one. This was the entire
purpose of `benchmark-unlock` and it is achieved.

**2. `graphical.target` is ~2.21s regardless of unlock method.** Passphrase boots
land at 2.194 / 2.210s and settled keyfile boots at 2.221 / 2.209s — the same
number. **So the repo's original standing rule was right all along**: `userspace`
and `graphical.target` *are* comparable across boot types, and the Phase 2
baseline of 2.095s stands unqualified.

**3. Discard the first boot after anything that regenerates the initramfs.**
Both first-boots-after-`add` are the outliers — 4.432s and 3.222s — and both
settle to ~2.21s within one or two reboots. This is now a measurement rule: after
`mkinitcpio -P`, reboot twice before recording a number.

## Two hypotheses raised and killed by this data

Recorded because the wrong turns cost real time and the same guesses will look
attractive again.

- **"The passphrase wait pre-warms hardware, so userspace only *looks* fast, and
  the 2.095s baseline is flattered."** Predicted a fast-typed passphrase boot
  would measure ~4.4s. It measured **2.210s**. Dead.
- **"The keyfile itself costs ~2.2s of userspace."** Rested entirely on boot -5's
  4.432s. Three more keyfile boots gave 3.222 / 2.221 / 2.209s. Dead — it was
  first-boot-after-change, not the keyfile.

Both were single-sample conclusions dressed as mechanisms. The cost of settling
them was three reboots.

## Open, and genuinely unexplained

**The keyfile's `kernel` phase is consistently ~1.2s longer than a fast-typed
passphrase boot** — 6.477 / 6.333 / 6.444 / 6.477s (n=4, tight) against 5.200s
(n=1). The keyfile should make this phase *cheaper*, not dearer.

**Plausible mechanism, untested:** LUKS2 keyslots are tried in order, and its
Argon2id KDF is deliberately tuned to roughly a second. The keyfile occupies the
second keyslot, so the hook may run a full KDF against keyslot 0, fail, then run
another against keyslot 1 — buying a wasted ~1s. If so it is an artifact of
having two keyslots rather than of keyfiles, it disappears with the keyfile, and
it costs nothing in the shipped product.

**Confirmed 2026-08-21 by `cryptsetup luksDump`, and it fits quantitatively.**
Both keyslots carry **identical** Argon2id parameters — `Time cost 9`,
`Memory 1048576` (1 GiB), `Threads 4` — and `cryptsetup benchmark` reports those
same parameters as cryptsetup's ~2000 ms target on this CPU.

`cryptsetup open` tries keyslots in order and both are `Priority: normal`, so:

| Boot | KDF runs | Why |
|---|---|---|
| Passphrase | 1 | slot 0 holds the passphrase and succeeds first |
| Keyfile | **2** | slot 0 is tried with the keyfile and fails, then slot 1 succeeds |

Because the slots are parameterised identically, the wasted run costs exactly
what the successful one costs. One run at boot therefore measures ~1.2s — lower
than `benchmark`'s 2000 ms target, which is expected: that figure is memory-only
with no storage IO and at a different CPU frequency state. **The predicted delta
is one full KDF, and the observed delta is 1.2s across four boots.** The
arithmetic closes.

**This one is an artifact of having two keyslots, not of keyfiles**, it vanishes
when the keyfile is removed, and it costs the product nothing as things stand.

### Consequence for the shipped installer — keyslot order is not cosmetic

Any second keyslot makes every boot pay one wasted ~1.2s Argon2 run *unless the
key used daily lives in slot 0*. That is not hypothetical: `CHOICES.md`
`luks-header-backup` already plans a **recovery key recorded off-machine**. Add
it carelessly and it is a permanent boot-time tax on a priority-2a metric.

**Rule for Phase 4: the daily passphrase goes in keyslot 0, and any recovery key
goes after it.** `archinstall` creates the first slot, so a recovery key added
afterwards lands later and is correct by default — but this must be *verified*
with `luksDump` rather than assumed, and re-verified if the passphrase is ever
rotated, since removing and re-adding a key can move it to a later slot.
