# Phase 3 — the picker half of `gr`, and the fix for the wrong first answer

Desktop, 2026-08-21 evening. Follows [`3.12`](3.12.gr-after-the-exclude.md),
which closed the server half: with the author's `pyrightconfig.json`, time to a
correct answer drops from **7.5 s to 469 ms**, and warm repeats run 46–178 ms.
This file measures what sits on top of that.

## 1. The picker, measured two ways

Each picker is handed the **same** list of LSP-reference-shaped rows and opened
5 times; figures are medians. Harness:
[`scripts/pickerbench.py`](../scripts/pickerbench.py).

**The two columns are two different signals, and they disagree — which is the
point.** *Content* is the time until the rows are actually present in a buffer,
polled every 4 ms. *Settled* is the time until the redraw stream went quiet for
200 ms, over a real attached UI. Content is the earliest moment the results
exist; settled is the last moment the screen is still moving.

| picker | load (one-off) | content n=5 | content n=1000 | settled n=5 | settled n=1000 | ΔRSS |
|---|---|---|---|---|---|---|
| **quickfix** (built-in) | — | **3.4 ms** | **6.6 ms** | 8.1 ms | 13.2 ms | +2.4 MB |
| **telescope** | 6.3 ms | 8.6 ms | 9.6 ms | 8.4 ms | 17.7 ms | +3.5 MB |
| **snacks.picker** (current) | 8.4 ms | 8.7 ms | 10.0 ms | 31.6 ms | 36.4 ms | +4.5 MB |
| **fzf-lua** | 8.2 ms | 27.0 ms | 28.1 ms | 122.4 ms | 123.2 ms | +9.3 MB |

Baseline nvim RSS 15.1 MB; ΔRSS is with the picker loaded and open on 1000 rows,
including child processes.

**The ordering is the same under both signals, but the magnitudes are not, and
one earlier conclusion does not survive.** A first pass reported only the
settled column and concluded snacks.picker was ~4x slower than telescope
(31.6 vs 8.4 ms). By content arrival they are **indistinguishable** — 8.7 vs
8.6 ms. The gap is entirely post-render work snacks does after the results are
already on screen. Any recommendation resting on that 4x was resting on an
artifact of which signal got measured.

**fzf-lua is last under both signals** — 3x the others on content, 4x on
settled — and **flat across every size**, the signature of a fixed cost rather
than a rendering one: it spawns the external `fzf` process on every open, paid
identically on 5 results and on 1000. This is an argument against the laptop's
`nvim-bunne` contender (`3.9`), which chose fzf-lua on *startup* time. `gr` is
the case where that pick loses.

**The pickers virtualise; quickfix does not.** Rows materialised on a 1000-row
list: quickfix **1000**, telescope 250, snacks 35, fzf-lua 35. The pickers render
one screenful and stay flat as `n` grows; quickfix writes the whole list into a
buffer, which is why it is the only one whose time climbs with `n` — and it is
still the fastest at 1000. This check exists because a settle detector will
happily report a fast time for a picker that rendered nothing; the numbers above
are meaningful only because the rows were confirmed present.

## 2. The wrong first answer

Measured here first, now folded into [`3.12`](3.12.gr-after-the-exclude.md) so
the two files cannot drift. In short: pyright answers from a partial index and
returns **1 reference** if asked immediately after `didOpen`, in every
configuration including the fast one. Waiting for the server's first
`publishDiagnostics` on the buffer returns the correct 5.

Across runs the gate cost **46–128 ms** (naive 423–660 ms, gated 466–788 ms) —
the spread is run-to-run variance on the same probe, not a difference in
configuration. Polling until two calls agree buys nothing over the simple gate
and costs an extra round trip.

It belongs in `BUDGET.md` as roughly **+50–130 ms, per `gr` on a cold buffer**,
in exchange for the feature being correct at all. Priority 2a measures "the
intended thing having happened" — an answer of 1 when the truth is 5 has not
happened, so this is the price of the feature working, not a regression.

## 3. What this means for `gr`

One `gr` on a warm server, with the exclude in place:

```
pyright references    46-178 ms   (3.12)
snacks.picker          ~9 ms content / ~36 ms settled
                      ─────────
                      ~55-215 ms
```

**The server dominates by an order of magnitude, and the picker is not the
bottleneck.** That was true when the picker gap looked like 4x and it is more
true now that snacks and telescope measure the same.

**Recommendation: keep snacks.picker.** Not because it wins — on content arrival
it ties telescope — but because it is already installed, it is within a
millisecond of the best plugin option on the signal that matters, and switching
would add `plenary.nvim` for no measurable gain. The earlier version of this
file recommended the same thing for the wrong reason ("telescope saves ~20 ms");
the honest reason is that there is nothing to save.

**Avoid fzf-lua for this binding**, and note that quickfix is genuinely the
fastest and costs zero plugins — worth considering if `gr` should be a plain
list rather than a fuzzy-filterable one. At 5 references, which is the real case
here, a fuzzy picker is arguably the wrong tool entirely.

**The 10-second `gr` is reproduced, and it is not the picker.** `3.12` shows
7.5 s without the exclude on the real repository, near 8-9 s with a venv
configured. Every picker in this table is a rounding error against that. The
gripe was a workspace-indexing problem end to end.

## Method note

The picker bench needed a real UI to measure rendering, and pynvim could not
provide one: its greenlet event loop raises `request from non-main thread` when a
second thread issues requests, and forcing it through `run_loop`'s `setup_cb`
crashed the interpreter. The harness therefore speaks msgpack-RPC over the
listen socket directly, with two connections — one attached as the UI recording
redraw timestamps, one issuing triggers. This is the same shape as `3.12`'s
decision to speak LSP directly after headless nvim proved unusable, and for the
same reason: **the editor's own client libraries were the least reliable part of
every measurement attempted this session.**
