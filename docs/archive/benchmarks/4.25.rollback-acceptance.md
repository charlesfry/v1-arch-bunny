# 4.25 — the snapshot rollback acceptance test

**2026-08-25, evening. `bunne-test`, at the keyboard.** The gate `snapshot-boot-entries`
named for itself: snapshot → canary → restore from the Limine menu → reboot → canary gone,
Docker data still there. Instrument: `benchmarks/instruments/4.25-rollback-acceptance.sh`.

## Result: ACCEPTANCE PASS

```
PASS: canary is gone — @ really was replaced.
PASS: both Docker subvolumes are still mounted after the rollback.
ACCEPTANCE PASS
```

**The decisive evidence is not the canary, it is the subvolume identity.** A missing file
could be explained several ways; a changed subvolume ID cannot.

| | before restore | after restore |
|---|---|---|
| `@` subvolume ID | 256 | **353** |
| `@` Parent UUID | `-` (an original subvolume) | `f45eac3d-2003-1041-98b7-f343243d6958` |
| snapshot 97 UUID | `f45eac3d-2003-1041-98b7-f343243d6958` | — |
| `/rollback-canary.txt` | present (written *after* 97) | gone |

`@`'s parent is now exactly snapshot 97. `RESTORE_METHOD=replace` genuinely swaps the root
subvolume. **This is the failure `snapper rollback` had here** — it looked correct and did
nothing, because `@` is pinned by name in two places. `limine-snapper-sync --restore`
replaces `@` *in place*, so the fstab and cmdline pins keep pointing at the right thing.

## The Docker half — gripes #1/#2 rollback isolation, now exercised

`alpine:3.21` (`48b0309ca019`) pulled before arming, present after the rollback. Both
subvolumes still mounted from `/etc/fstab`, caps intact:

```
0/329   9.79MiB   100.00GiB   @containerd
0/330  140.00KiB   50.00GiB   @dockervol
```

The DA round said the promotion's *rollback isolation* was unexercised. **DA round 19
then scoped this claim back, and it was right to.** `@containerd` and `@dockervol` are
top-level subvolumes mounted from `/etc/fstab`; a snapshot of `@` structurally *cannot*
contain them and a replacement of `@` *cannot* touch them. So this confirms the wiring is
as believed — it does not discover anything about isolation.

**And the realistic recovery case is untested.** The restored snapshot was taken minutes
earlier from the same `@`, with the same `/etc/fstab`, kernel and initramfs. **A snapshot
from before the Docker-subvolume promotion (~18:00 the same day) carries an `/etc/fstab`
with no `@containerd`/`@dockervol` lines. Restoring it would silently leave Docker writing
into `@`, uncapped — gripe #1 reintroduced by the recovery mechanism itself.** That case
is both more likely than the one tested and more damaging, and nothing here touches it.
**Checked, 2026-08-26 — the hazard is real, and bounded.** Mounting every snapshot and
grepping its `/etc/fstab`: of 24 snapshots, **two have no `@containerd`/`@dockervol` lines**
— snapshot **1** (Aug 23 22:38, the install) and snapshot **75** (Aug 25 17:21, hours
before the promotion). Restoring either would put Docker back inside `@`, uncapped, and
then snapshot it — gripes #1 *and* #2 reintroduced by the recovery mechanism.

**But neither is reachable from the Limine menu.** The menu carries 78–100, and all 23 of
those have both fstab lines. So the boot-menu recovery path cannot reach the dangerous
snapshots today; only a manual `snapper`/`btrfs` restore could.

**And on a fresh BunnE install the hazard does not exist at all**, because
`docker-storage-quota` creates the subvolumes at install time, so no snapshot ever
predates them. This is an artifact of `bunne-test`'s mid-life migration.

**The durable lesson survives that scoping, though:** *any* change to `/etc/fstab`,
subvolume layout, or mount topology silently divides the snapshot history into "safe to
restore" and "restores into a differently-shaped machine", and nothing in the boot menu
distinguishes them. The menu shows a date and a description, not whether the snapshot's
idea of the filesystem still matches the disk.

**Correction to the cap story, found while arming.** This Docker uses the **containerd
image store** (`Storage Driver: overlayfs`, `driver-type: io.containerd.snapshotter.v1`).
Image bytes land in `/var/lib/containerd`, not `/var/lib/docker` — the alpine pull moved
`@containerd` 0 → 9.77 MiB while `@dockervol` stayed at ~140 KiB. The surviving cap proof
from 4.24 was `dd` against **`@dockervol`**, which holds no images. **The cap that gripe #1
is actually about is the 100 GiB on `@containerd`, and it remains unexercised.**

## What this does NOT prove

- **The way back is asserted, not demonstrated.** Snapshot 98 (`pre-rollback`) holds the
  old `@` and appears in the menu, but it was never booted and never restored back. The
  gate's third leg — *"backup entry puts the machine back"* — is still inferred. Under the
  repo's own "prove it, do not infer it" rule that is an open item, not a pass.
- **The GUI restore gesture is unproven.** The successful restore was typed at a terminal.
  The notification path was *attempted* and failed (below); it has never been seen to work.
- **Same kernel on both sides.** 7.1.9-arch1-2 throughout. A rollback across a kernel
  change is untested, which is the case `limine_history` exists for.

## Four defects in the recovery path

Recovery is priority 1, and these are all in it.

1. **The GUI restore fails silently.** Clicking "Restore now" on the critical mako
   notification: pkexec authenticated and ran the command as root — journal, 21:32:01,
   `COMMAND=/usr/bin/limine-snapper-sync --restore --no-mutex` — which exited immediately
   on a stale lock, and kitty closed with the error inside it. From the author's seat:
   password prompt, then nothing at all. This is `02-functionality.md`'s "fail loudly" rule
   broken **by the recovery mechanism itself**, and it is the `jupyter-in-neovim` shape of
   bug: not broken, just quiet.
2. **The restore lock has no staleness detection.** `/usr/bin/limine-snapper-sync:202`:
   ```bash
   if [[ -e "${RESTORE_LOCKFILE}" ]]; then
       warning_msg "limine-snapper-restore is already running."
       exit 1
   fi
   ```
   A bare existence test on a zero-byte `/run/lock/limine-snapper-restore.lock`. No PID, no
   age, no flock — the real flock (`BOOT_PARTITION_LOCK`) is a different file and was free
   throughout. Cleanup is `trap cleanup_all EXIT`, so **any interrupted restore wedges all
   future restores until someone deletes the file by hand.** Self-inflicted here (I killed
   a blocked prompt), but a crash or power loss mid-restore produces it identically — and
   the machine most likely to lose power mid-restore is the one that needs to restore.
3. **It takes `snapper-cleanup.service` down with it.** Same stale lock:
   `21:31:13 snapper-cleanup.service: Failed with result 'exit-code'`. So a wedged restore
   also silently stops snapshot retention — the mechanism behind gripe #2. Recovered to
   `active` once the file was removed.
4. **Restore cannot be scripted.** Two interactive prompts (`[r/l/c]`, then `Description
   for backup subvolume @:`), the second undocumented, and the input is ANSI-rendered so it
   wants a pty. There is no `--yes`. The binary's entire flag set is `--add --info --list
   --no-force-save --remove --restore --restore-kernels --update` — **unknown flags are
   silently ignored, not rejected**: `--help` performed a sync and rewrote
   `/boot/limine.conf`, and `limine-snapper-restore`'s own `--restore --no-mutex` passes a
   flag that does not exist. **`install.sh` can document recovery; it can never automate
   it.**

The one component that behaved well: `limine-snapper-watcher` detected the read-only
snapshot and said so — `WARNING: You are in the read-only Btrfs. limine-snapper-watcher
stopped.`

## Boot-path notes

- **`limine.conf` survived the restore without renumbering.** Checked from NixOS against
  the read-only-mounted ESP before booting back — `/+Arch Linux` at visible index 1,
  `//linux` (`rootflags=subvol=@`) at index 2, so `default_entry: 2` still selects the
  restored root. `check-limine.sh`: *ok — default_entry 2 resolves to a bootable entry, 40
  boot() file(s) present* (36 before; the backup added a kernel pair). `/boot` 14%.
- **The snapshot boots read-only and cannot be scribbled on.** `findmnt` reports the mount
  option as `rw`, but `btrfs property get / ro` is `ro=true` — the subvolume property wins.
  A `mkdir` under `/mnt` failed accordingly.
- **`efibootmgr` entry IDs, settled.** `resume.md` said "0001 (or 0000)"; it is
  **`Boot0001* Limine`** → `\EFI\limine\limine_x64.efi`. `Boot0000* Arch Linux` is the
  fallback `\EFI\BOOT\BOOTX64.EFI` on the same ESP, and `Boot0007* Linux Boot Manager` is
  systemd-boot on `p1`, which is first in `BootOrder` — hence a plain reboot landing NixOS.
- **`--bootnext` is one-shot and is consumed by the reboot**, so a test that reboots twice
  needs it set twice. Costs a round trip through NixOS each time.

## Procedure that worked, for the installer's recovery docs

1. `sudo efibootmgr --bootnext 0001`, reboot.
2. At the Limine menu (`timeout: 1` — tap ↓ immediately): `Snapshots` → the snapshot →
   `linux`.
3. Booted inside it, at a **real terminal**: `sudo limine-snapper-sync --restore` → `r` →
   a description for the backup subvolume.
4. `sudo efibootmgr --bootnext 0001`, reboot. Let it auto-boot entry 2; no keypress.

Step 3 must not be interrupted. If it is, delete
`/run/lock/limine-snapper-restore.lock` before retrying — nothing else reports why.
