# 4.27 — the `@containerd` cap, exercised at last (and it bit the whole machine)

**2026-08-25, late. `bunne-test`.** `docker-storage-quota` caps `@containerd` at 100 GiB
and `@dockervol` at 50 GiB. 4.24's surviving proof was `dd` against **`@dockervol`**, and
4.25 established that **`@dockervol` holds no images** — this Docker uses the containerd
image store, so image bytes land in `/var/lib/containerd`. So the cap gripe #1 is actually
about had never been exercised. This is that test, at a synthetic 200 MiB.

## The headline

**The first overflow is exemplary. A subsequent one took the entire filesystem
read-only — `/` and `/home` included — and needed a reboot to clear.**

## What was run

`sudo btrfs qgroup limit 200M 0/329 /`, from 100 GiB, with `@containerd` at 9.79 MiB.

| step | result |
|---|---|
| `docker pull python:3.13-slim` (~112 MiB) | success; usage **112.18 MiB / 200 MiB** |
| `docker pull node:22` (~1 GB) | **fails cleanly** — see below; usage pinned at exactly **200.00 MiB** |
| same pull, retried | **`read-only file system`** — the filesystem was gone |

The clean failure, in full:

```
failed to copy: failed to send write: write /var/lib/containerd/io.containerd.content.v1
.content/ingest/ffef.../data: disk quota exceeded
```

`docker pull` exits **1** (checked without a pipe — piping to `tail` reports `tail`'s
status and reads as success, which is its own trap for any script that wraps this).
Both daemons stayed `active`, `python:3.13-slim` and `alpine:3.21` remained listed, and
the cap held to the byte. **That is exactly the behaviour the row wants.**

## What went wrong on the retry

```
BTRFS: error (device dm-0) in rollback_verity:459: errno=-122 Quota exceeded
       (failed to drop verity items in rollback 6719)
BTRFS info (device dm-0 state E): forced readonly
BTRFS error (device dm-0 state E): failed to rollback verity items: -122
```

Docker's surface error was `write /var/lib/containerd/io.containerd.metadata.v1.bolt/
meta.db: read-only file system`, which is a symptom, not the cause.

**The mechanism.** btrfs turns on fs-verity for content it stores; when enabling verity
fails it must *roll back* the verity items, and dropping them needs metadata space. The
quota denies that space. A rollback that cannot complete is not a recoverable error, so
btrfs aborts the transaction and forces the filesystem read-only.

**Why it hit `/` and `/home`.** This is the part that matters, and it is architectural
rather than incidental: **a qgroup limit is scoped to a subvolume, but forced-readonly is
scoped to the whole btrfs filesystem.** `@`, `@home`, `@containerd`, `@dockervol`, `@log`,
`@pkg` and `@snapshots` are all one filesystem on `/dev/mapper/cryptroot`. The kernel
message names `device dm-0`, not the subvolume. Verified rather than inferred: `touch`
failed under both `/root` and `/home/bunne`, and `findmnt` reported `/` as `ro`.

**Recovery needed a reboot.** `mount -o remount,rw /` was refused (exit 32) — btrfs will
not clear an error-state readonly in place. After the reboot: `rw`, zero forced-readonly
events, `@containerd` restored to a 100 GiB cap, and `docker system prune -af` reclaimed
189.8 MB including **39 MB of orphaned ingest** the failed pull left behind.

Two things stayed writable throughout and are worth knowing for recovery: **`/boot`**
(vfat on `p5`, a different filesystem) and **efivars** — `efibootmgr --bootnext` still
worked, which is how the box was steered back to Arch while its root was read-only.

## What this means for `docker-storage-quota` — a decision, not a tweak

The row's premise is that a cap converts gripe #1 (Docker fills the disk, machine dies)
into a bounded, survivable failure. **Half of that holds.** The bounded part is real and
was proven here. But the failure mode on the far side of the cap is not merely "Docker
stops"; under the right operation it is "the machine goes read-only and needs a reboot",
which is a **priority-1 `it just works` failure** and arguably worse than the disk filling
up, because it arrives without warning at a threshold the user chose.

Options, none of them picked here:

- **Accept it.** The first overflow is graceful; you have to keep pushing to reach the bad
  path. Cheapest, and the risk is real but not routine.
- **Put Docker on its own filesystem**, not merely its own subvolume — a separate LUKS
  volume or a loopback image. Then forced-readonly is contained to Docker, which is what
  the cap was supposed to achieve. Costs an install-time partitioning decision.
- **Cap below the danger zone and monitor** — keep the qgroup as an accounting mechanism,
  and let the existing disk-usage alert fire long before the cap, so the cap is never
  actually reached in normal use. Cheapest correct-ish option; leans on C9.
- **Drop the qgroup cap** and rely on monitoring alone. Reopens gripe #1.

## Reproduced on a loopback image — deterministic, and quota is the trigger

`benchmarks/instruments/4.27-verity-quota-repro.sh`. A 3 GB loop-mounted btrfs, quota on,
a 200 MiB file in a subvolume, and the qgroup limit tightened to leave **64 KiB** of
headroom against a Merkle tree needing roughly **1.6 MB**. Enabling fs-verity then
produces, on the loop device, the identical kernel signature seen on `bunne-test` —
same function, same line, same errno:

```
BTRFS: error (device loop0) in rollback_verity:459: errno=-122 Quota exceeded
       (failed to drop verity items in rollback 257)
BTRFS info (device loop0 state E): forced readonly
```

**4 runs, 4 reproductions.** This is deterministic, not a fluke, and `4.26`'s rule is now
satisfied. The blast radius stayed inside the loop device every time.

**Scope it honestly:** this shows the mechanism is real *given tight enough headroom*. The
real-box event used a **200 MiB synthetic** cap and the loopback uses **64 KiB** of
headroom chosen to be smaller than the Merkle tree. **Nobody has shown that ordinary
Docker use against the shipped 100 GiB cap ever reaches this state**, and it is one kernel
(`7.1.9-arch1-2`) and one btrfs version.

**Two controls bound the claim:**

| setup | verity enable | filesystem |
|---|---|---|
| quota, **10 MiB** headroom | succeeds | stays `rw` |
| quota, **64 KiB** headroom | `EDQUOT` | **forced readonly** |
| **no quota**, filesystem 100% full (`df` shows 0 available) | **succeeds** | stays `rw` |

**The third row is not a control, and DA round 19 rejected the use it was put to.** At
`df` 100% btrfs still had metadata reserve, so verity succeeded and **the Merkle write was
never refused in that arm**. An arm in which the thing under test never happens establishes
nothing about how btrfs handles an ENOSPC-denied verity write.

The defensible statement is narrower: **a qgroup limit produces the denial trivially and
deterministically, and I could not construct one via ENOSPC.** That is a claim about how
reachable the two conditions are, not about how they are handled.

**So this does not settle option 1 below.** The first write-up used it to argue that the
cap *introduces* a failure mode the uncapped machine lacks; that argument is withdrawn.
What remains is that the cap makes the denial condition easy to reach, which is a weaker
and different point.

**Upstream-shaped.** A rollback path that cannot fail cleanly under a quota the kernel
itself enforces looks like a btrfs bug rather than a misconfiguration, and the harness
above reproduces it from a clean image in about a minute — which is the shape of thing
`CLAUDE.md` says to report upstream rather than hack around.

## Honest scoping

- **No longer n=1** — see the section above. Reproduced 4/4 on a loopback image with the
  identical kernel signature, so the mechanism is established. What is still n=1 is the
  *Docker* route to it: only one real `docker pull` sequence reached `rollback_verity`,
  and how easily ordinary Docker use gets there is not characterised.
- **The graceful path is n=1 too**, though it is the less alarming direction to be wrong in.
- **The architectural claim needs no reproduction.** That forced-readonly is
  filesystem-wide while qgroups are per-subvolume is how btrfs is built, and it was
  observed directly on `/home`.
- **The trigger is fs-verity, and containerd is what supplies it.** A workload that never
  enables verity should never reach `rollback_verity`. Whether anything else in a BunnE
  install enables verity under a capped subvolume is not surveyed.

## Process note — this was a self-inflicted outage

The test pointed a destructive quota experiment at a subvolume sharing a filesystem with
`/` and `/home`, on a machine that cannot be rebooted without the author. The blast radius
was foreseeable from the fact that qgroups and forced-readonly have different scopes, and
it was not thought through before the test ran. **The lesson is not "do not run the test"
— the test found a real priority-1 defect that three earlier sessions had missed — it is
that a destructive test wants its blast radius established first, and a loopback image was
available the whole time.**

## ANSWERED 2026-08-26 — option 4: drop the caps, keep the qgroups for accounting

**Author, 2026-08-26**, choosing from the four options in §"a decision, not a tweak":
*option 4 — drop the cap, monitor only.* Applied the same morning.

The reasoning that makes this coherent rather than a retreat: **gripe #1's actual shape is
slow growth** — a disk filling over weeks of project work — and against slow growth a
6×/day alert is a perfectly good instrument (`benchmarks/raw/p4-disk-alert-draft/NOTES.md`
proved meter 2 fires and names the culprit). What the qgroup *limit* added on top of that
was not protection against the gripe; it was a new priority-1 failure mode that the gripe
never had. A disk that fills gives ENOSPC to the process filling it. A qgroup that fills
can give the whole filesystem forced-readonly until a reboot. Trading the second for the
first is a straight priority-1 win.

**What actually changed on the box** (`bunne-test`, 2026-08-26):

```
btrfs qgroup limit none 0/329 /   # @containerd, was 100 GiB
btrfs qgroup limit none 0/330 /   # @dockervol,  was 50 GiB
```

Both subvolumes stay exactly as they are — top-level, fstab-mounted, `noatime,compress=zstd:1`.
Nothing about `snapshot-bloat` changes: keeping Docker out of every snapshot of `@` is the
*subvolume*'s doing, and gripe #2 never depended on the limits at all.

### The acceptance test, because the answer rests on a claim nobody had run

Option 4 rests on **"the *limit* is the trigger, not the accounting"** — if quota
accounting alone could deny the Merkle write, dropping the limits would fix nothing and
the alert's numbers would be bought at the price of the same outage. That had not been
tested. `4.27-verity-quota-repro.sh` grew a third arm, `--accounting`: quota enabled, no
limit set.

Paired on `bunne-test`, same kernel (`7.1.9-arch1-2`), same session, same loopback recipe:

| arm | quota | limit | verity | loop fs |
|---|---|---|---|---|
| default (positive control) | on | 64 KiB headroom | `errno=122 Disk quota exceeded` | **ro** — `rollback_verity:459` |
| `--accounting` ×3 | on | **none** | **ENABLED** | **rw** |

3/3 for the shipped configuration against 1/1 for the control on the same box the same
morning, on top of the earlier 4/4. **The limit is the trigger.**

**And the accounting is exact.** The arm reads the qgroup back: `209731584` bytes for a
200 MiB `/dev/urandom` file — the number the alert needs, to the byte, with no limit set.

**One trap found doing it, and it is the alert's trap too:** the first run reported
**16 KiB** for that same subvolume. Qgroup figures count *committed* extents, so a read
taken before the extents are on disk is not stale by a little, it is wrong by four orders
of magnitude. The instrument now `sync`s first. The alert does not need to — btrfs commits
every 30 s and the alert polls every four hours — but anything that reads a qgroup
immediately after writing must, and the installer's own cap verification is exactly such a
thing.

### Live, on the real subvolume, through Docker

With both limits `none`, `docker pull python:3.12-slim`:

```
pull exit: 0
0/329   292.00KiB -> 103.05MiB   none   none   @containerd
```

Accounting tracked a real pull; exit 0, `/` still `rw`, zero failed units, all three of
`docker.socket` / `docker.service` / `containerd.service` healthy. Note `docker image ls`
calls it **178 MB** against the qgroup's **103 MiB** — the compressed-bytes point the row
already makes, now applying to the *meter* rather than to a cap.

**The image was left in place deliberately.** Every previous test of this layout ran
against an empty `@containerd`, which is precisely the state in which the migration's
central failure mode (nested per-layer subvolumes) cannot surface.

### What this costs, and the question it opens

The qgroups now do accounting and nothing else, and btrfs qgroup accounting is not free —
it adds work to metadata operations for every subvolume on the filesystem. Before it was
the mechanism enforcing a priority-1 cap, so its cost was the price of the feature. Now it
buys one number in a 6×/day notification, and **that trade has never been measured here**.
Raised as open question 28 rather than settled: either it is unmeasurable and stays, or it
is real and the alert should get its number some other way.
