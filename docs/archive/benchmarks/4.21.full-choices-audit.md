# 4.21 — Full CHOICES.md ↔ machine reconciliation audit

Successor to [`4.17.package-audit.md`](4.17.package-audit.md), which audited a
slice and found four lying rows plus a dead package. This is the **whole-table**
pass: every `picked`/`rejected` row's `Packages` cell checked against what is
actually installed on `bunne-test`. Motivation is priority-1 and the "understand
every line / verify on the machine / prove don't infer" doctrine: **the Phase-4
installer is generated *from* these rows**, so a row that disagrees with reality
is a broken installer line waiting to ship.

## Method (reproducible)

- Ground truth: `pacman -Qq` (683 pkgs) and `pacman -Qqe` (88 explicit) from the
  box, `2026-08-25 ~09:30`, box on Arch, kernel `7.1.9-arch1-2`.
- `scratchpad/audit.py` parses every 7-column table row, extracts the `Packages`
  cell (expanding `foo-{a,b}` brace-lists, stripping backticks/em-dash), and
  cross-checks: picked ⇒ every named package installed; rejected ⇒ none
  installed; plus the reverse — explicit packages named by **no** picked row.
- 80 rows parsed with a status.

## Finding 1 (NEW, real) — the Hyprland stack is back, via `dms-shell`

The `compositor` row is `rejected` and its cell names `hyprland kitty
xdg-desktop-portal-hyprland`. `kitty` is legitimately present (it is the picked
terminal, sharing the cell as a trial artifact). **`hyprland` should not be** —
`compositor-cleanup` was closed when Hyprland was removed (23 pkgs). It is
installed again, with its whole stack: `hyprland`, `hyprcursor`, `hyprgraphics`,
`hyprlang`, `hyprtoolkit`, `hyprutils`, `hyprwayland-scanner`, `hyprwire`,
`hyprland-guiutils`.

Mechanism, traced on the box:

```
dms-shell (explicit, MUB candidate)
  └─ depends: dms-shell-compositor   (virtual)
       └─ provider chosen: dms-shell-hyprland
            └─ depends: hyprland  → the whole hypr* stack
```

`xdg-desktop-portal-hyprland` was **not** pulled (good — so this is the library
stack, not a full portal re-install). DankMaterialShell was measured running on
*niri* first-try (morning report), yet the installed provider is
`dms-shell-hyprland`, not a niri variant. So the MUB exploration silently
reversed a closed decision.

**Not urgent** (dms-shell is not running; it is kept for the author's play), and
**not mine to fix** (removal is a root op tied to the MUB keep/sweep decision).
It becomes actionable at the MUB keep/sweep call: sweeping `dms-shell` takes the
Hyprland stack with it; keeping it means MUB-via-DMS currently implies a Hyprland
dependency unless a `dms-shell-niri` provider is selected instead.

**Resolved:** `dms-shell-niri` *does* exist (`extra/dms-shell-niri 1.5.3-1`, a
3.0 KiB meta depending on `dms-shell niri` — no hyprland). So the keep path is
clean: swap the provider (`pacman -S dms-shell-niri`, remove
`dms-shell-hyprland`, then `pacman -Rns $(pacman -Qtdq)` to drop the orphaned
`hypr*` stack). Keeping DMS for MUB need not drag in Hyprland at all.

## Finding 2 (NEW, real) — the picked editor's runtime deps have no rows

`pyright`, `ripgrep`, `fd` are installed and named by **no** `Packages` cell.
They are not incidental: `pyright` is the LSP the `gr` gripe was fixed around,
and `ripgrep`/`fd` are what Telescope/snacks.picker shell out to. The `editor`
slot is `picked` (LazyVim), but its cell does not enumerate them.

DA split (the two are not the same case):

- **`ripgrep` + `fd` are system-PATH binaries** that Telescope/snacks and `gr`
  shell out to; nothing in the Neovim runtime provides them. If they are absent,
  find-in-files and the file picker **silently degrade on a fresh machine** —
  the `man-db`→`less` shape exactly. These want a package-list entry regardless
  of how the editor config is written. **Solid.**
- **`pyright` is ambiguous.** LazyVim's Mason can auto-install the LSP at
  runtime, in which case a pacman row would be redundant. Whether it comes from
  pacman or Mason is a Phase-4 *config* decision (the shipped `nvim` config is
  still a draft, `nvim-p4`), not something this audit can settle. Flag it there,
  don't assume the row.

(`fzf` + `lazygit` are the same class but already tracked as open question #8;
`imagemagick` is named in the `jupyter-in-neovim` cell — the parser only flagged
it because of a trailing `;`.)
