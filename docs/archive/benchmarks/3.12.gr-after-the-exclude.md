Desktop, 2026-08-21 evening. `~/tradeswell/ds-ml-platform`, pyright **1.1.407**
from Mason — the author's own server. Target `get_adstock_saturated_media_jax`,
defined at `tasks/fm_np/code/core/transform.py:132`.
Harness: [`scripts/lspref.py`](../scripts/lspref.py) and
[`scripts/lspref-coldstart.py`](../scripts/lspref-coldstart.py).

**Ground truth is 5 references in 3 files.** `grep -rnw` finds 8, but 3 are in
`tasks/lw_mmm/`, which defines its *own* function of the same name at
`code/core/transform.py:15`. Those are a different symbol; a correct
find-references must not return them. Pyright gets this right.

> **This file was rewritten after its first version got the headline backwards.**
> The first pass concluded "the answer was wrong, not slow" — because it made
> only three rapid calls and read the resulting `1` as permanent. It is not
> permanent. Given time to settle, pyright returns the correct 5 in every

> supposed. What follows is the corrected measurement.

## The result

**Time to a *correct* answer**, measured on the real repository, each figure the
median of two reproducible runs:

| config | venv | first answer | **time to correct answer** |
|---|---|---|---|
| **author's `pyrightconfig.json`** | — | 5 ✅ | **469 ms** |
| **no config at all** (pre-16:00 state) | — | 5 ✅ | **7,540 ms** |
| author's config + `mmm` | `mmm` | 5 ✅ | 1,393 ms |
| no config + `mmm` | `mmm` | 5 ✅ | 9,281 ms |

**16x, and the gripe is reproduced.** 7.5 s without the exclude — and the
author's editor has a venv configured, which puts the real figure near 8–9 s.
"10+ seconds even for a symbol with only a few references" is exactly this.

The venv rows were measured through a symlink farm; the config rows were
measured both ways and agree to 3 ms (farm 468 ms, real repo 469 ms), so the
farm is faithful.

Warm repeat calls, once the server has settled, are **46–178 ms** with the
exclude — well inside priority 2a.

## The trap: pyright answers before it is ready

**Asked immediately after `didOpen`, pyright returns 1 reference — in every
configuration, including the fast one.** It answers from a partial index and
marks nothing as partial. `3.10` found this for basedpyright on `rich` and
`pandas`; it is confirmed here for pyright on the author's own repo.

This is what made the first version of this file wrong, and it is a real hazard
in its own right: a user who runs `gr` immediately gets `1`, and `1` looks like a
plausible answer for a function that might be unused.

**Waiting for the server's first `publishDiagnostics` on the buffer fixes it**:

| strategy | first answer | total |
|---|---|---|
| ask right after `didOpen` | **1 ref ❌** | 423 ms |
| wait for `publishDiagnostics`, then ask | **5 refs ✅** | 469 ms |
| wait, then poll until two calls agree | 5 refs ✅ | 839 ms |

With the exclude in place the gate costs about **50 ms** and converts a wrong
answer into a right one. Polling for agreement buys nothing over the simple
gate and costs another round trip. **This is the one editor-config change worth
making**, and it needs a `BUDGET.md` row.

Note what the gate does *not* do: it does not make the slow case fast. Without
the exclude the gate still returns the correct answer — after 7.5 s. The gate
fixes correctness; the exclude fixes speed. They are independent and both are
wanted.

## Method, and a harness that had to be thrown away

`scripts/lspref.py` drives `pyright-langserver --stdio` directly — no editor, no
picker — and reports **every** call rather than a best-of.

**The intended harness was headless Neovim and it produced nothing usable.**
`vim.lsp.start` attached in 194 ms and pyright's notifications flowed, but
pyright never answered a single **request**: `documentSymbol`, `hover`,
`definition` and `references` all timed out at 20 s on a *two-file* project. The
wire log shows the requests sent and nothing returned. The same server, given
the same requests by a 60-line raw stdio client, answers hover and references in
**0.69 s**.

Every nvim-derived number this session was discarded, including a 182 s "cold
call" against this repo and a 121 s call against a 70-file subdirectory. Those
were read at the time as evidence that workspace size was not the cause; they
were evidence of nothing. **The control that caught it was running the cheapest
possible request, `hover`, on a two-file project** — when that also took 20 s,
the harness was the only remaining suspect.

Pull diagnostics were tested as the explanation and cleared: with
`textDocument/diagnostic` advertised, pyright answered the diagnostic request in
624 ms and references in 178 ms. The cause is still unknown. It is specific to a
minimal `--clean -u NONE` configuration — the author's LazyVim works — but it is
worth understanding before trusting any nvim-side measurement.

The no-exclude arms were run two ways: through a symlink farm (one link per
top-level entry, minus `pyrightconfig.json`, so import roots are preserved), and
directly on the repository with the gitignored config moved aside for ~15 s and
restored under a trap, checksum-verified byte-identical. A first farm attempt
linked the repo as a single `src/` child and had to be scrapped — that moves the
import root, so `from tasks.fm_np...` stopped resolving and the arm returned 1
reference for an entirely unrelated reason.
