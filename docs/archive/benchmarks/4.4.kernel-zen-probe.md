# 4.4 — linux-zen probe (informational; not DA-gated, changes no row)

The `kernel` row queued "zen as a measured bake-off of its own." First data,
same night as the row: `arch-bunny`, linux-zen 7.1.9-zen1-2, 2 measurement
boots (discard boot honored — initramfs regenerated), same instruments and
battery as 4.2. Raw: `raw/battery.arch-zen-boot[12].log` (on the box:
`~/log/`).

| metric | mainline (3-4 boots) | zen (2 boots) |
|---|---|---|
| kitty warm median | 130.1 / 130.2 / 130.4 / 131.7 ms | **127.1 / 128.5 ms** |
| fuzzel warm median | 20.9-21.5 ms | 21.8 / 21.6 ms |
| boot userspace | 2.69 / 2.77 / 3.71 s | 3.72 / 3.63 s |
| boot total | 16.8-17.7 s (loader 2.27) | 16.6 s (loader 1.27 — post-trim, not kernel) |
| PSS 3rd sample | 198.9-201.8 MB | 206.0 / 205.3 MB |

Reading: zen shows a consistent-direction ~2-3% (3-5 ms) kitty spawn
improvement at n=2, nothing on fuzzel, no visible boot win (userspace
variance is wifi-association-driven at this n), and a ~5 MB PSS excess of
unknown attribution. **Nothing here displaces the mainline pick** — the row
was picked on priority 1 (one boring kernel) and the measurable 2a delta so
far is at the edge of noise. If zen is ever re-argued, it needs ≥3 boots per
side and an input-latency metric (where 1000 Hz / BORE would actually show),
not spawn medians.

Housekeeping: linux-zen is still installed with a limine entry
(`/Arch Linux (zen)`); mainline is the default. Cost while it stays: a
second initramfs build on every kernel-adjacent update. Remove it or keep it
for more samples — author's call (morning-report queue).
