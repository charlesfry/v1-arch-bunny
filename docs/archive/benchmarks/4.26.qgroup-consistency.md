# 4.26 — does a btrfs qgroup byte cap still enforce when the accounting is "inconsistent"?

**Short answer: yes, in every controlled test.** This file mostly exists to retract an
alarm I raised on one uncontrolled observation, and to record two real hazards found
while chasing it — one of which I caused.

Machine: `bunne-test` (Arch), 2026-08-25 evening, over ssh.
Instrument: [`instruments/4.26-qgroup-consistency.sh`](instruments/4.26-qgroup-consistency.sh).

## Why this was worth an hour

`docker-storage-quota` is the answer to gripes #1 and #2, and its entire mechanism is a
btrfs qgroup byte cap. `disk-alert` reads qgroup meters. So *"the cap silently stops
enforcing under condition X"* would be a priority-1 finding about the two features the
project exists for.

The trigger: after the evening's reboot the standing `WARNING: qgroup data inconsistent,
rescan recommended` line was back, and an ad-hoc canary run in that state wrote **the
full 64 MiB against an 8 MiB cap** — where the same canary is refused at 8 MiB when the
accounting is clean.

## What replication actually showed

**1. The "a pacman transaction dirties the accounting" trigger does not replicate.**
Three runs of install-and-remove with snap-pac taking pre/post pairs: the accounting
stayed **consistent** every time. Whatever dirtied it earlier, it was not simply "a
package transaction".

**2. The cap enforces while inconsistent.** With the state induced deliberately
(`btrfs quota disable` / `enable`, which is the reliable way to reach it — see the hazard
below), against an 8 MiB cap:

```
WARNING: qgroup data inconsistent, rescan recommended
dd: error writing '/var/lib/docker/.qgroup-canary': Disk quota exceeded
8232960 bytes written against an 8M cap
0/330   7.98MiB   7.98MiB   8.00MiB   @dockervol
```

Refused at 7.98 MiB against 8.00 MiB — **the same byte-exact refusal as the clean-state
arm**, which was re-run immediately afterwards as a control and produced an identical
`8232960`. The flag warns that *reported* numbers may be stale; it did not stop the limit
being applied.

**3. So the original observation is withdrawn.** One uncontrolled run, unexplained, not
reproduced in four subsequent attempts across both states. It is recorded here rather than
deleted so that if a 64 MiB write ever passes an 8 MiB cap again, someone knows it has
been seen once — but **nothing in `docker-storage-quota` changes on the strength of it**,
and no claim about lapsed enforcement enters the ledger.

**The process point is the one worth keeping.** A DA round had, an hour earlier, rejected
two conclusions of mine for resting on single uncontrolled samples. I then nearly wrote a
scary claim about the project's headline mechanism on exactly that basis. The reflex that
saved it was cheap and should be the default: *before writing it down, try to make it
happen again on purpose.*

## Hazard 1 (self-inflicted): `btrfs quota disable` destroys snapper's qgroup

Inducing the inconsistent state via `btrfs quota disable /` + `enable /` has a cost the
manual does not put in front of you: **it wipes all qgroup data, including snapper's
`1/0`**, while `/etc/snapper/configs/root` keeps `QGROUP="1/0"` pointing at something that
no longer exists. It also drops the `docker-storage-quota` caps (100 GiB / 50 GiB), which
have to be re-applied by hand.

Snapper's own `SPACE_LIMIT=0.08` / `FREE_LIMIT=0.2` cleanup reads that qgroup, so this
quietly disables the byte-cap half of `snapshot-system` — the answer to gripe #2 —
while leaving the config file looking correct. Nothing warns.

Recovery, on the supported path: `sudo snapper -c root setup-quota` recreates `1/0`, and
existing snapshot subvolumes get reattached to it — an explicit re-assign pass over all
45 reported *"already a member"* for every one, so `setup-quota` does the whole job.
Caps re-applied with `btrfs qgroup limit`, then `btrfs quota rescan -w /`.

**Verified restored by the consumer, not just by the accounting**: `snapper -c root list
--columns number,used-space` prints a per-snapshot size again, which is precisely the
figure that requires `1/0`. `1/0` reports 3.97 GiB referenced. *(Ignore
`btrfs qgroup show`'s `<0 member qgroups>` note on a level-1 qgroup — it lists child
qgroups of the same level, not members, and says nothing about whether the restore
worked.)*

**For the ledger:** anything that runs `btrfs quota disable` on a BunnE machine must
re-run `snapper -c root setup-quota` and re-apply the docker caps afterwards, or the
machine ends up with a snapshot config that references a qgroup that is not there. This
is the same shape as the `@`-rollback hazard `docker-storage-quota` already documents:
a mechanism that keeps *looking* configured after the thing it depends on has gone.

## Hazard 2: a cap canary must use incompressible data

Carried over from 4.24 and re-confirmed here. The filesystem is `compress=zstd:1`, so
32 MiB of `/dev/zero` referenced 1.18 MiB and sailed under an 8 MiB cap. Every canary in
this file uses `/dev/urandom`.

## Instrument note

The committed script's arm B — "force inconsistency with a pacman-paired transaction" —
**did not fire in three runs**, so as written it tests one arm and reports the other as
untriggered rather than silently passing. That honesty is deliberate, but it means the
script cannot on its own reproduce the result above; the induced route was run by hand
because automating `quota disable` would mean automating hazard 1. Anyone re-running this
should induce by hand and restore snapper's qgroup afterwards.

## Status

No `CHOICES.md` row changes. `docker-storage-quota`'s cap is where it was: proven to
refuse a write at the byte, on `@dockervol`, in both accounting states — and still
unproven through docker itself and on `@containerd`, per 4.24.
