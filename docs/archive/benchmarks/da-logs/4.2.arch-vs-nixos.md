DA agent: fresh Sonnet, nix-bunne `DA-BRIEFING.md` role verbatim. This DA

## DA critique (verbatim)

1. **The headline table's own sample-size label is false for the two rows carrying the OS-attribution claim.** Every NixOS column header reads "(n=3 boots)," but the prose two paragraphs down says kitty *warm* medians come from **2 boots** (7-8) and kitty *cold* comes from **5 boots** (4-8), of which only 3 numbers are shown in the table. A reader who trusts the table header — which is the whole point of a headline table — walks away thinking this is a clean 3-vs-3, when it's actually 3-vs-2 for the metric doing the causal work ("kitty is 15% faster... not NixOS the OS"). That's not a caveat, that's the table lying about its own N.
2. **Selective display of the cold-boot data.** You collected cold-boot numbers on 5 NixOS boots but the table shows exactly 3 (257.5/256.4/263.5). Where did the other two go? Either they were dropped because they were embarrassingly good/bad for the story, or because they came from the aborted-teardown boots and someone quietly decided those 2 didn't count for cold either — in which case the "colds from those boots kept" framing in the disclosed warts is only half-true and the file doesn't say which half.
3. **The document promises a fix for the greetd confound, then doesn't deliver it.** The intro explicitly says: "so desktop-ready is compared via the niri.service activation timestamp, not graphical.target" — because Arch's `graphical.target` ≈ getty-ready while NixOS's includes greetd, making the raw targets non-equivalent. The headline table then reports **only** "userspace to graphical.target," with zero niri.service-activation row anywhere in the file. The exact confound the authors identified as disqualifying was never actually neutralized — the report just reverts to the disqualified metric and hopes nobody checks the intro paragraph against the table. This is a self-contradiction inside the same document, not a subtle inference on my part.
4. **Instrument-version mismatch (v1.5 Arch vs v2 NixOS) isn't even in the permanent record.** It only exists in the conversational disclosure I was handed, not in `4.2.arch-vs-nixos.md` itself. That means the moment this file gets cited in `CHOICES.md` or `da-logs/`, that wart evaporates — nobody reading the artifact later will know the two sides ran different code for the metric ("kitty is faster, and it's kitty's fault not the OS") that most needs identical instrumentation. And "timing code untouched, diff is a dict lookup before the loop" is *asserted*, never demonstrated by running both instrument versions back-to-back on one OS/boot to show statistically indistinguishable output. This repo's own CLAUDE.md says "prove it, do not infer it" and treats an unexercised safety mechanism as broken until demonstrated — apply that standard here and this claim is unproven, not proven.
5. **Fuzzel is a weak control for the kitty delta it's being asked to validate.** Fuzzel is a tiny launcher; kitty is a GPU-accelerated terminal with font shaping and a documented Nix wrapper-exec/store-path-resolution layer. The report's own hypothesis for the kitty delta is "wrapper exec indirection, store-path resolution... possibly build flags" — mechanisms that scale with dependency count and binary weight. Fuzzel passing (≤1.5 ms apart) proves the compositor+IPC+spawn plumbing is equal. It does **not** prove the wrapper/linking overhead the report is about to blame for the kitty gap is equal, because fuzzel barely exercises that mechanism. One thin, structurally dissimilar control does not license offloading a 15-30% delta from "the OS" onto "kitty's own path."
6. **"Same session composition" was not actually held constant before measuring — it was measured-then-subtracted after the fact.** greetd vs getty-autologin, bluetooth on vs off, Docker on vs off, live audio stack vs socket-dormant — these are all *configuration choices the experimenters made*, not organic OS behavior. If the goal was isolating "NixOS-the-OS" from "the workload on top," the honest move is to disable Docker/Bluetooth/Bitwarden autostart and switch to autologin *before* running, not to measure a loaded box and subtract named line items afterward. Post-hoc subtraction assumes no interaction effects (e.g., does greetd's PAM session setup slow anything else it touches that isn't captured by its own PSS line?) — that assumption is never tested.
7. **Kernel-version mismatch undercuts a design decision already on record, and gets caveated selectively.** `CHOICES.md` line 82 explicitly says mainline was picked for the Arch box because it's "apples-to-apples against NixOS's mainline kernel." The 4.2 report then discloses "NixOS 26.05's kernel per its channel" — NixOS channels pin a specific (often older, LTS-class) kernel, not necessarily the same version as Arch's rolling 7.1.9. If that assumption was wrong, the entire boot decomposition (initrd/kernel init, driver probe time) carries a kernel-version confound. The report caveats kernel mismatch for the *kitty* delta only ("rests on the fuzzel control, not kernel equality") and never once raises it against the boot-time numbers, where it's arguably more relevant since boot literally is kernel-init time.
8. **The one genuinely apples-to-apples data point in the whole report gets hand-waved instead of investigated.** Same compositor binary, niri, running on both OSes: 93.9 MB vs 86.0 MB PSS — a 9.2% gap, dismissed in a single parenthetical ("same compositor within 10% on two different builds/kernels"). This is the cleanest available signal for whether the OS/toolchain itself adds overhead, independent of workload composition, and it says yes, measurably — yet it gets less scrutiny than anything else in the document. That's backwards: the investigative effort should chase the one number that isn't confounded by "well NixOS also runs Bitwarden," not wave it off.
9. **Firmware-phase variance (4.9-6.1s on NixOS, ~24% spread) is suspicious and unexplained.** Firmware/POST time on identical hardware should be nearly constant and OS-independent. A quarter-second-to-a-second-plus spread there suggests either measurement noise in the `systemd-analyze` firmware timestamp, or that reboot method (power-cycle vs warm `reboot`, which changes RAM-training/fast-boot behavior) wasn't held identical and balanced across the two OS blocks. If that variable leaked, it sits underneath every downstream phase boundary in the boot decomposition.
10. **Loader-timeout asymmetry was known before the run and not neutralized.** limine's `timeout: 2` vs systemd-boot's ~6.1s default menu wait is flagged as "config, not capability," with "trimming limine to 1s is queued" noted for the *Arch* side only. If isolating "OS-controlled" boot time was the actual goal, both loader timeouts should have been matched (or both minimized) before collecting data, not left asymmetric with a fix queued for one side only.
11. **No dispersion, no significance testing, anywhere.** Every comparison is medians or point-ranges with zero stdev/IQR/min-max shown for the underlying per-boot n=10 spawn samples. A 15% median-vs-median gap on an n=2-vs-n=3 boot comparison, with no reported spread, is not evidenced as signal — it's evidenced as "the medians differ," which is a different and weaker claim.
12. **No pre-registered decision threshold anywhere in the file**, despite this being an explicit, named project rule ("state what number would change the recommendation, before collecting it," `METHODOLOGY.md`). The interpretation section reads like a story constructed to fit the numbers after seeing them ("given (1), the delta lives in kitty's own startup... not in NixOS-the-OS") rather than a test of a claim staked out in advance. That is exactly the failure mode the rule exists to block.
13. **The `free`-used row (~647 vs ~1,200 MB) sits in the same headline table as the PSS numbers**, inviting anchoring on a raw ~2x figure that isn't this project's chosen RAM metric and carries its own undisclosed confounds (kernel slab/page-table accounting, and no statement anywhere that swap/zram configuration was matched between the two boxes).
14. **This DA pass itself was not given what the standing process requires.** `DA-BRIEFING.md` mandates DA receive "the raw data behind it (all samples, not a summary/average with the samples discarded)" and "the test script(s) used to collect the data." I got a markdown summary and a prose description of instrument behavior — not `spawnbench.py`/`pss-sum.sh` source (which don't even exist anywhere in either repo I can find), and not the raw n=10-per-boot arrays. I cannot independently verify "~0.3ms per poll," "no CLI exec in measured path," or "timing code untouched." I'm being asked to bless claims about instruments I've never seen — which fails the gate's own evidentiary bar before we even get to the data.
15. **Stakes check, since it changes how much slack this deserves:** `CHOICES.md`'s `os-base` row rejected NixOS on 2026-08-20 explicitly "on argument, not measurement" and marked itself "provisional until exercised... a VM afternoon after Phase 3 settles the compositor slot is enough." This 4.2 report is evidently meant to be that exercise. Given the ledger itself demands a real measured verdict here, the density of open holes above (mislabeled N, an abandoned fix for a named confound, an unverified instrument swap, an unexamined same-binary delta, a kernel-version assumption already broken relative to a prior committed decision) means this document is not yet the rigorous measurement that row is waiting for. Using it to close that row now would repeat the exact sin the ledger note was written to guard against.

**Verdict: Rejected outright pending rerun.** [Closing text retained in full in the agent transcript; summary: conclusion (1) fuzzel-as-control and the RAM composition breakdown could survive with caveats in isolation, but the causal claims lean on broken/mislabeled/unexamined foundations. Rerun demands: instruments hashed/committed, config-matched or minimized loader timeouts, equal boot counts actually delivered, the promised niri.service metric collected, dispersion reported, pre-stated thresholds.]
