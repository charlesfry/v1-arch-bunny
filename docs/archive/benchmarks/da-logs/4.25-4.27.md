## D — the worst of them, and it was in a commit message

**Claim as written:** *"a control shows the cap INTRODUCES the failure mode rather than
merely reaching it sooner."*

**The control does not show that.** The ENOSPC arm filled a 700 MB loop filesystem to
`df` 100% and then enabled fs-verity — **and verity succeeded.** The Merkle-tree write was
therefore *never refused* in that arm. A control in which the thing being tested never
happens is not a control; it establishes nothing about how btrfs handles an ENOSPC-denied
verity write, because no such denial occurred.

What can honestly be said is much narrower: **I was unable to construct an ENOSPC denial,
while a qgroup limit produces one trivially and deterministically.** That is a statement
about how easy the two denial conditions are to reach, not a comparison of how btrfs
handles them. The stronger framing was then used to argue *against* option 1 ("accept
it") in `open-questions.md` — i.e. a flawed control was allowed to push a live design
decision. That is exactly the failure this gate exists to catch.

The write-up in `4.27` already stated the caveat correctly in its own table commentary;
the commit message and the open-question text did not, and the open-question text is what
the author will actually read when deciding. **Corrected in place.**

## G — a control-void boot comparison, and round 18 already flagged this exact error

Tonight's text put **17.658 s (getty) against 17.344 s (greetd)** and called it "the wash
4.19 predicted". Both are **single `systemd-analyze` samples from different boots on a
box whose state changed between them** — packages removed, a filesystem forced read-only
and recovered, wallpapers restarted. The within-config spread that `4.19` actually
measured (greetd 2.906/2.690 s vs autologin 3.244/2.708 s userspace) **exceeds the 0.314 s
gap being quoted**. Quoting a 0.3 s difference from n=1 vs n=1 as evidence of anything is
the same control-void mistake DA round 18 rejected for `nvidia-open`, in the same repo,
three days earlier.

The conclusion "boot is a wash" is *correct* — but it is correct **because `benchmarks/4.19`
measured it with n=2 per arm**, not because of tonight's numbers. Tonight's figures should
never have been presented as support. **Corrected: the decision now cites 4.19 and tonight's
single samples are marked as non-evidence.**

Note this does not disturb the decision itself. greetd was rejected on *feel* by the
author, which is a legitimate and explicitly-anticipated basis for this row.

## H — "reboot-verified" was doing far too much work

The box booted Arch three times through the edited `limine.conf`. That proves **the file
parses and does not brick boot.** It does not prove either directive does what it says:

- **`timeout: 3` was never timed.** Nobody measured the menu window. The claim that
  recovery is now reachable in three seconds instead of one rests on the config file
  saying so. A stopwatch, or the author reporting the window feels different, would settle
  it; neither happened.
- **`hash_mismatch_panic: no` is wholly unexercised.** It only does anything when there
  *is* a hash mismatch, and there was none. **Nothing whatsoever has been demonstrated
  about this setting's behaviour on this machine** — only that setting it does not break a
  normal boot. Per this repo's own rule, a safety mechanism that has never been exercised
  is broken until demonstrated, and this one is squarely in that class. It is testable:
  corrupt a byte of a `boot():` file on the ESP and observe warn-instead-of-panic. That
  test has not been run.

**Corrected**: both are recorded as *"config applied, boot unaffected"*, and
`hash_mismatch_panic` is flagged as an unexercised safety mechanism.

## B — "closes the leg" is too generous

The test showed `alpine:3.21` and both subvolume mounts surviving one rollback. That is
worth having. But:

1. **It was already true structurally.** `@containerd` and `@dockervol` are top-level
   subvolumes mounted from `/etc/fstab`; a snapshot of `@` cannot contain them and a
   replacement of `@` cannot touch them. The test confirms the wiring is as believed — it
   does not discover anything about isolation.
2. **The realistic recovery case was not tested.** The restored snapshot was taken
   *minutes earlier* from the same `@`, with the same `/etc/fstab`, same kernel, same
   initramfs. **A snapshot from before the Docker-subvolume promotion (~18:00 the same
   day) has an `/etc/fstab` with no `@containerd`/`@dockervol` lines** — restoring that
   would silently leave Docker writing into `@`, uncapped, which is gripe #1 restored by
   the recovery mechanism. That is a foreseeable, specific, untested failure and it is
   more likely than the case that *was* tested.
3. **Gripe #1 is in worse shape after tonight, not better**, given `4.27`.

**Corrected**: scoped to "the wiring behaves as designed across one same-generation
rollback", with the older-snapshot fstab hazard written up as a named risk.

## E — "resolved" overstates a correlation

Solid-colour swaybg measured **8.1 MB RSS / 2.2 MB PSS** on `bunne-test`; `BUDGET.md`
carried **8.2 MB** from a session-7 measurement. 8.1 ≈ 8.2 is *consistent with* the old
number having been RSS. It is not proof: the original was taken on **a different machine**
(the author's Omarchy desktop) in a different session, and no one has produced the original
command. A 0.1 MB agreement between two different machines is suggestive, not
identification. **Corrected to "consistent with", with the residual possibility named.**

Also, all three swaybg figures were **single samples taken 2–3 s after start**, not steady
state, and the tool might release decode buffers later. **Discharged 2026-08-26** by
sampling each mode at 3 s, 30 s and 120 s: 2.2/2.2/2.2, 9.1/9.1/9.1, 18.0/18.0/18.0 MB
PSS — flat in all three modes, so swaybg does not release buffers later and the cold
sample *is* the steady number. Note this tests the actual hypothesis rather than just
repeating the measurement, which three identical cold samples would not have done.
The cross-machine 8.2-vs-8.1 inference above is unaffected and stays "consistent with".

## C — survives, with the reachability gap named

The reproduction is genuinely good: identical `rollback_verity:459` / errno -122 /
forced-readonly signature, 4/4, blast radius contained, harness checked in. What it
establishes is that **the mechanism is real and deterministic given a tight enough quota
headroom.**

What it does **not** establish is that a **100 GiB** cap on a real machine ever reaches
that state. The real-box event used a **200 MiB synthetic** cap, and the loopback used
**64 KiB** of headroom deliberately chosen to be smaller than the Merkle tree. Nobody has
shown that ordinary Docker use against the shipped cap gets there. The headline sentence —
"the cap can take the whole machine read-only" — is true but invites a stronger reading
than the evidence supports. One kernel (`7.1.9-arch1-2`), one btrfs version. **Scoping
sentence added.**

## A and F — what survives intact

**F survives, and the caveat was then discharged.** The concern was that crop review used

## The pattern across D, G, E and H

All four are the same failure: **a real result written up one notch stronger than its
evidence.** None of the underlying work was wrong; the reproduction is solid, the numbers
were taken correctly, the box does boot. What went wrong each time was the sentence
*about* the result — "a control shows", "resolved", "reboot-verified", "a wash" — each
claiming a category of certainty the evidence had not earned, and three of the four
landed in the documents the author reads to make decisions rather than in the raw
write-up. **Write-ups were more careful than commit messages and open-question text this
session; those are the artefacts that need the same discipline, because they are the ones
that get acted on.**
