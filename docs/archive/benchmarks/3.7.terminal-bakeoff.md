# Phase 3 — the terminal bake-off, all four measured identically

`bunne-test`, 2026-08-21, **idle (load 0.00)**, live niri session. Run by
`~/t-terminals`, which measures every installed candidate the same way so the
numbers are comparable — 4 warmups discarded, 8 runs measured, per terminal.

| Terminal | cold (ms) | input-rt (ms) | flood (ms) | RSS (MB) | kitty graphics |
|---|---|---|---|---|---|
| **foot** | **12.2** | 0.660 | **166** | **23** | no |
| alacritty | 78.3 | 0.673 | 233 | 254 | no |
| **kitty** | 177.6 | 4.217 | 220 | 297 | **YES** |
| ghostty | 279.7 | **0.434** | 282 | 309 | YES |

- **cold** — spawn until a shell is actually *running inside* the new window.
  Chosen because some terminals return as soon as they have handed off, which
  would otherwise report a window that does not exist yet.
- **input-rt** — `ESC[6n` parse-and-reply. The terminal's input loop. **Not**
  keystroke-to-photon, which adds compositor, protocol and presentation and
  needs a high-speed camera (`04-plan.md` Phase 1 step 4).
- **flood** — 200k lines of base64. Throughput, i.e. keeping up with output.
- **kitty graphics** — `kitten icat --detect-support`. `02-functionality.md` C5
  makes this a **hard requirement** for inline Jupyter plots.

## What C5 actually costs

This bake-off exists because the author asked the right question: not "which is
fastest" but **"what is the graphics-protocol requirement costing us?"**

**~165 ms per window and ~274 MB**, against the fastest compliant option. foot
starts **14.6x faster** than kitty, uses **13x less memory**, and is fastest on
throughput as well. That is a steep price and it is now measured rather than
assumed.

## Why kitty is still picked

**The Sixel escape hatch was investigated, not dismissed.** `image.nvim` does
ship a Sixel backend and explicitly lists foot as supported — so foot is not
strictly incapable of inline plots. But its own README rates that backend
**"pretty crap performance, although very usable with
`only_render_image_at_cursor=true`"**, against **"best in class... works great
and is very snappy"** for the Kitty backend.

That settles it, because of what this project is for. *"Jupyter notebooks are a
pain"* is **one of the three headline gripes** BunnE exists to fix
(`CLAUDE.md`), `CHOICES.md` `jupyter-in-neovim` was proven working only days ago
**on kitty**, and moving to a backend its own author calls poor would risk
re-creating the exact problem — trading a fixed headline feature for terminal
launch time.

**The two-terminal split was considered and dismissed by the author**: foot for
daily use, kitty bound separately for notebooks. *"Needing 2 terminals for
different tasks is expensive."* Two configs, two themes, two keybind sets and a
"which one am I in?" problem is a priority-1 cost paid every day against a 2a
gain — and priority 1 outranks 2a.

## Surprises worth keeping

1. **ghostty is the slowest to start**, despite being Zig with no Python. On
   Linux it is a GTK4 + libadwaita application and pays that init: 170 shared
   objects to kitty's 100.
2. **kitty has the *worst* input round-trip** — 4.217 ms, roughly 6-10x the
   others. It does not matter, because all four are far below one 60 Hz frame
   (16.7 ms) and none can be felt. **Optimising the invisible axis while
   accepting a visible 165 ms would be exactly what `BUDGET.md` rule 6
   forbids.**
3. **alacritty is not even the best non-compliant option.** foot beats it on
   every axis. The predecessor's terminal is dominated by a package one tenth
   its size.
4. **Faster startup does not imply faster throughput.** ghostty starts slowest
   *and* floods slowest; alacritty starts 6x faster than kitty but floods
   slower. The axes are independent and have to be measured separately.

## Revisit if

- `image.nvim`'s Sixel backend stops being "pretty crap" — that would make foot
  viable outright and is worth ~165 ms and ~274 MB per window.
- Notebook use drops to near zero, which would demote C5 from hard requirement
  to preference.
